Engineering Notes

DART Insight는 어떻게 만들어졌나

발표에서는 서비스가 무엇을 하는지만 다룹니다. 이 페이지는 그 뒤에 있는 구조와 기술 과제를, 코드 위치와 결정 기록(ADR)을 따라 개발자가 바로 찾아 읽을 수 있게 정리했습니다.

ⓘ

숫자와 설정값은 2026-11-13 main 기준 코드와 docs/adr/에서 확인한 값입니다. 경로를 누르면 GitHub에서 파일이 열립니다(저장소 권한 필요).

1 · Architecture

호출은 한 방향, 일은 서비스마다 하나씩

화면은 백엔드만, 백엔드는 AI 서버만 부릅니다. 반대 방향 호출은 없습니다(ADR-0002).

서비스맡는 일맡지 않는 일
frontend/화면, 분석 상태 폴링, 원문 뷰어 점프FastAPI·OpenDART 직접 호출
backend/OpenDART 호출과 접수번호 기준 캐시, 분석 작업 상태, 증감 계산, 근거 재확인, 에이전트 Tool 실행, LLM 일일 한도원문 파싱, LLM 호출
ai-server/원문 ZIP 파싱·구조화, 문장 변화 탐지, BM25 근거 검색, 요약·설명 생성과 검증, 에이전트 한 단계(LangGraph)DB 저장, OpenDART 호출, Tool 실행
mcp-server/외부 AI 에이전트용 읽기 도구쓰기, 내부 API 호출

분석 하나가 지나가는 길

  1. 요청보고서 두 개의 접수번호로 POST /api/analyses. 같은 조건의 결과가 있으면 재사용(ADR-0014)
  2. 작업 번호 발급PENDING으로 저장하고 바로 응답. 실행은 스레드 풀(AnalysisRunner)
  3. 자료 준비backend가 OpenDART 원문·재무를 받아 캐시. 원문 구조화는 ai-server에 맡김
  4. 비교·계산재무 증감은 backend 코드가, 문장 변화는 ai-server가 찾음
  5. 요약·검증ai-server가 LLM으로 설명을 쓰고 근거 ID·숫자·표현을 검사
  6. 저장 후 완료결과 저장과 COMPLETED를 한 트랜잭션으로. 화면은 상태를 폴링하다 결과를 조회

모든 요청은 X-Trace-Id 하나로 묶입니다. backend TraceIdFilter가 정하고(요청 헤더에 있으면 그 값), 로그 MDC와 ai-server 호출 헤더에 넣습니다. ai-server는 TraceIdMiddleware로 이어받습니다(ADR-0005).

2 · Engineering Challenges

기술 과제 다섯 가지

과제마다 무엇이 문제였는지, 무엇을 정했는지, 코드에서 어디를 보면 되는지 정리했습니다.

과제 1 · 원문 파싱

깨진 공시 XML을 빠짐없이 읽고, 문단마다 안정된 근거 ID 붙이기

ADR-0009

문제

OpenDART 원문은 XML이라고 하지만 닫히지 않은 태그와 이스케이프 안 된 &가 흔합니다. 엄격한 XML 파서(lxml 등)는 이런 곳에서 내용을 조용히 버립니다. 버린 문단은 근거로 쓸 수 없습니다.

결정

Python 표준 html.parser로 관대하게 읽고, 원문의 표 셀·문단 태그 수와 읽은 수를 대조해 빠진 게 있으면 PARTIAL로 남깁니다. 블록마다 {접수번호}#B{블록 번호} 근거 ID를 붙입니다.

동작

  1. ZIP에서 본문 {접수번호}.xml만 고릅니다. 압축 해제 크기가 300MB를 넘으면 FILE_TOO_LARGE로 끝냅니다.
  2. 인코딩을 XML 선언 → UTF-8 → CP949 순서로 시도합니다.
  3. 이스케이프 안 된 &만 고친 뒤 _DartReader(HTMLParser)에 넣습니다. DOM 트리는 만들지 않고 태그 이벤트로 블록을 바로 만듭니다.
  4. 목차는 SECTION-n과 첫 TITLE로, 블록은 P(문단)·TABLE(표)로 나누고 문서 순서대로 1부터 번호를 매깁니다.
  5. 태그 수가 맞지 않으면 PARTIAL, 읽지 못하면 FAILED와 사유 코드(INVALID_ZIP 등)를 돌려줍니다.
근거 ID 예:  20260814003699#B812
             └ 접수번호 ┘ └ 블록 번호(문서 순서)
!

블록 번호는 파서 규칙에 묶여 있습니다. 파서를 고치면 같은 원문의 번호가 바뀔 수 있어서, PARSER_VERSION(지금 dart-xml-2)과 분석 버전을 함께 올립니다.

과제 2 · 숫자와 문장의 신뢰

LLM은 계산하지 않고, 근거를 확인한 문장만 내보내기

ADR-0006ADR-0015ADR-0013

문제

LLM은 증감률을 틀리게 계산하거나, 원문에 없는 숫자·출처를 그럴듯하게 만들어 냅니다. '저평가', '매수' 같은 가치판단도 섞입니다. 금융 정보에서는 한 번만 틀려도 서비스 전체를 믿을 수 없게 됩니다.

결정

숫자는 backend 코드가 계산해 LLM에 그대로 넣습니다. LLM이 쓴 문장은 ① 근거 ID ② 숫자 ③ 금지 표현을 코드로 검사하고, 실패하면 최대 2번 다시 쓰게 한 뒤 그래도 안 되면 '검토 필요'로 끝냅니다.

숫자: backend

  • 증감액은 long으로 Math.subtractExact, 증감률은 BigDecimal로 나눕니다(HALF_UP).
  • 계산할 수 없으면 0이 아니라 null과 사유 코드를 남깁니다. 사유 코드는 13가지입니다(예: PREVIOUS_ZERO, TURNED_PROFIT, PERIOD_MISMATCH).
  • 재무 사실 문장도 코드(FinancialFacts)가 씁니다. LLM은 문장 변화 설명과 회사 설명만 씁니다.
  • 저장 전에 EvidenceVerifier가 증감액이 두 값의 차와 같은지, 근거 접수번호가 맞는지 다시 봅니다.

문장: ai-server

  • 근거 ID가 없거나 넘겨준 후보에 없는 ID면 반려합니다(summary/validate.py).
  • 인용한 원문에 없는 숫자, '두 배·절반' 같은 크기 표현을 막습니다(llm/grounding.py).
  • 정규식 규칙 6개로 표현을 검사합니다: 매매 추천, 투자 조언, 목표주가, 주가 예측, 가치판단, 수익 보장(compliance/expressions.py).
  • 공시 원문은 프롬프트에서 구분 태그로 감싸 지시가 아닌 자료로 넣습니다.

과제 3 · 근거 문단 찾기

임베딩 없이, 글자 2개 단위 BM25로 설명 후보 문단 찾기

ADR-0036

문제

'매출액이 왜 늘었나'를 설명하려면 보고서 문단 수백 개(실측 490~760개) 중에서 해당 계정을 다루는 문단을 골라 LLM에 넘겨야 합니다. 형태소 분석기는 모델만 약 88MB라 CI·시연 서버 부담이 컸고, 벡터 DB는 별도 인프라가 필요했습니다.

결정

검색어가 '매출액'처럼 띄어쓰기 없는 명사구라는 점을 이용해, 공백을 뺀 글을 글자 2개 단위로 나눈 Okapi BM25를 라이브러리 없이 약 30줄로 구현합니다. 색인은 요청마다 만들고 저장하지 않으며, 같은 입력이면 같은 순서가 나옵니다.

40자 기준은 실측으로 정했습니다. 20자에서는 SK하이닉스 매출액 1위가 출처 한 줄(※ 출처: IDC 2024년 12월, 매출액 기준)이었습니다. BM25가 짧은 글을 우대하기 때문입니다. 40자로 올리자 경영진단의 설명 문단이 1위가 됐고, 60자도 결과가 같았습니다. 아래 직접 해 보기에서 바꿔 볼 수 있습니다.

과제 4 · 분석 작업

수십 초 걸리는 분석을 비동기 작업으로, 결과를 다 저장한 뒤에만 '완료'

ADR-0004ADR-0014

문제

공시 받기·파싱·LLM 요약까지 한 요청에서 기다리면 시간 제한에 걸립니다. 상태를 아무 데서나 바꿀 수 있으면 결과 일부만 저장된 채 '완료'로 보이거나, 끝난 작업이 다시 '진행 중'이 될 수 있습니다.

결정

요청 → 작업 번호 → 상태 조회 → 결과 조회로 나누고, 상태는 코드의 허용 전이표로만 바꿉니다. 결과 저장과 COMPLETED는 AnalysisResultService 한 곳에서 한 트랜잭션으로 처리합니다.

현재 상태갈 수 있는 상태
PENDINGRUNNING, FAILED
RUNNINGCOMPLETED, FAILED
COMPLETED없음(끝 상태)
FAILED없음(끝 상태)
  • 표에 없는 전이는 IllegalStateException으로 거부합니다.
  • 서버가 다시 뜨면 끝나지 않은 분석을 실패로 바꾸고, 30분 넘게 멈춘 분석도 실패로 처리합니다.
  • 같은 보고서 쌍·같은 분석 버전(지금 m2-20)이면 저장된 결과를 다시 씁니다. 분석 방식이 바뀌면 버전을 올립니다.
  • 'COMPLETED는 AnalysisResultService만 만든다'는 규칙을 ArchUnit 테스트(onlyResultServiceCompletesAnalysis)가 지킵니다.

과제 5 · 에이전트 채팅

AI는 다음 할 일만 고르고, Tool 실행과 근거 확인은 backend가

ADR-0044ADR-0045ADR-0059ADR-0063

문제

채팅이 회사 재무·문장 변화·용어를 조회하려면 Tool이 필요합니다. AI 서버가 Tool을 직접 실행하면 DB 접근·권한 확인·캐시를 AI 서버에 다시 만들어야 하고, 단방향 호출 규칙도 깨집니다. 채팅은 LLM 호출이 잦아 비용도 문제였습니다.

결정

대화 상태와 Tool 실행은 backend가 갖고, ai-server는 LangGraph로 '한 단계'만 계산해 TOOL_CALLS · FINAL · OUT_OF_SCOPE 중 하나를 돌려줍니다. 쓰기 Tool(노트 담기 등)은 실행하지 않고 사용자 확인 버튼으로 돌려줍니다.

  • 체크포인터·메모리·LangChain 도구 노드·interrupt를 쓰지 않아 ai-server가 무상태로 남습니다.
  • 한 채팅의 모든 왕복이 같은 X-Trace-Id를 씁니다.
  • 근거는 7가지 종류로 두고, 그 채팅에서 실제로 조회된 자료인지 backend가 다시 확인합니다(ADR-0048).
  • Tool 고르기 호출이 자료가 충분하면 답 초안까지 써서 호출 수를 줄입니다(ADR-0049).

3 · MCP Server

왜 만들었나

수익화 전략에서 첫 판로를 '사용자의 AI 에이전트가 결과를 가져가는 것'으로 정했습니다. 에이전트는 MCP로 외부 도구를 부릅니다. 에이전트가 OpenDART를 직접 읽으면 섹션·표 짝짓기, 코드 계산, 근거 ID 검증 같은 우리 가치가 빠지므로, 검증을 마친 결과를 주는 통로가 필요했습니다.

결정

별도 폴더 mcp-server/에 두고 backend 공개 API(/api/**)만 부릅니다. ai-server·OpenDART·DB는 직접 부르지 않습니다. 과금과 API 키가 아직 없으니 읽기 도구 7개만 엽니다. LLM 비용이 드는 분석 요청 같은 쓰기는 막아 둡니다.

가격 원칙 '기계가 읽는 가격·한도'에 따라 크레딧을 도구 설명과 응답에 미리 적습니다. 시제품이라 실제 과금은 0이고, 1크레딧 ≈ 100원은 요금제 가설입니다.

에이전트를 위한 안전장치

  • 서버 안내(instructions)에 사용 순서와 "숫자를 다시 계산하지 말고, 문장을 인용할 때는 근거 위치를 함께 밝혀라"를 적습니다.
  • 응답마다 DART 출처와 '투자 조언 아님' 안내를 붙입니다.
  • backend 오류는 과금 없이 코드 (상태): 메시지 · traceId=… 도구 오류로 돌려줍니다. 연결 실패는 MCP_BACKEND_UNREACHABLE.
  • 요청마다 mcp-로 시작하는 추적 ID를 붙여 backend 로그에서 에이전트 호출을 구분합니다.
검토한 다른 방법고르지 않은 이유
backend 안에 MCP 엔드포인트인증·과금 없이 원격으로 열면 누구나 부를 수 있음. 시제품 때문에 backend에 Java MCP 라이브러리를 들일 이유가 없음
ai-server 안에 MCPai-server는 backend가 부르는 내부 서버라 호출 방향이 거꾸로 됨
에이전트가 OpenDART를 직접 읽게 둠짝짓기·코드 계산·근거 검증 같은 우리 가치가 빠짐
쓰기 도구까지 바로 열기LLM 비용이 드는 일을 과금·한도 없이 외부에 열게 됨
!

시제품의 한계: 사용자가 자기 컴퓨터에서 stdio로 실행해야 하고(원격 MCP 없음), 이미 끝난 분석만 읽습니다. 쓰기 도구와 원격 전송(streamable-http)은 크레딧 장부·API 키를 만들 때 과금·키별 한도 ADR을 먼저 쓰고 엽니다.

선택 1 · 분석 실행

분석은 비동기 작업, 결과를 다 저장한 뒤에만 완료

ADR-0004 · 0014 · 0042
  • 공시 받기와 AI 요약에 수십 초가 걸립니다. 작업 번호를 먼저 주고 화면이 몇 초마다 묻습니다.
  • 허용된 전이만 코드의 표로 관리해, 모든 결과가 저장된 뒤에만 '완료'로 보입니다.
  • 같은 두 보고서는 저장된 결과를 다시 쓰고, 방식이 바뀌면 버전을 올립니다.

AI는 다음 할 일만 고르고, 실행은 백엔드가

5 · Guardrails & Delivery

규칙은 테스트가 지키고, 배포는 되돌릴 수 있게

backend 계층 규칙 · ArchUnit

ArchitectureTest.java · ADR-0016

  • Controller → Service → Repository·Domain 계층 방향
  • Controller는 Repository를 직접 쓰지 않음
  • Repository는 Service·Controller에 기대지 않음
  • 다른 도메인의 Repository를 직접 쓰지 않음
  • 분석 완료는 AnalysisResultService만
  • 도메인 패키지 사이 순환 없음

2-VM 배포와 자동 복구

infra/jenkins/README.md · deploy-ai-backend.sh

  • VM1: backend·웹·DB, VM2: ai-server와 Jenkins 빌드 에이전트
  • 검사 → 같은 커밋으로 이미지 3개 → AI·backend 배포 → 웹 배포
  • DB 마이그레이션은 REVIEWED_MIGRATIONS에 등록된 SHA-256과 맞을 때만 진행. 두 VM 모두 사전 검증을 통과해야 교체 시작
  • 교체 전 이전 이미지를 rollback-{release_id}로 보관, 기동 확인(2초×30회) 실패 시 이전 이미지로 복구. backend가 실패하면 AI도 함께 되돌림
  • 교체 전 DB 덤프를 만들지만 역마이그레이션은 자동으로 하지 않음

6 · Fact Check

이전 발표 자료의 기술 수치 점검표

11/12까지 쓰던 이전 발표 자료(41장)의 '5대 기술 난제' 수치를 코드·ADR과 대조했습니다. 지금 발표 자료(17장)는 오른쪽 값만 씁니다. 지금 발표에 쓰는 숫자는 발표 대본 문서 머리에 있습니다.

발표 자료판정확인한 사실
StAX 스트리밍 파서, 메모리 80MB 고정다름Python 표준 html.parser로 본문 전체를 읽음. 크기 제한은 압축 해제 300MB뿐이고 80MB 근거 없음(ADR-0009)
원문 앵커 #접수번호#B{n}, 영구다름형식은 {접수번호}#B{n}. 파서 버전에 묶여 있어 파서가 바뀌면 번호도 바뀔 수 있음
BigDecimal로 100% 계산일부 맞음증감액은 long, 증감률만 BigDecimal
근거 ID 없으면 기각, 최대 2회 재생성, 금지어 검사맞음근거 ADR은 0006·0013·0015(발표 자료의 0062·0064는 다른 결정)
BM25 검색 45ms근거 없음실측은 색인 17~19ms, 계정 4개 검색 1.8~1.9ms(ADR-0036)
BM25 최소 40자, 경영진단 ×1.5맞음사업의 내용 ×1.3도 있음. 가중치는 잠정값
PENDING→RUNNING→COMPLETED 단방향, X-Trace-Id맞음PENDING→FAILED도 허용. 추적 ID 근거는 ADR-0005(0014 아님)
Tool 고르기 Haiku, 답 Sonnet(2-Tier)다름ADR-0063 이후 모든 작업이 claude-haiku-5-5. 2-Tier는 OpenAI 설정에만 남음
호출당 $0.0009, 비용 95% 절감조건부OpenAI 모델(#742) 단계당 0.0168→0.0009달러(약 94.6%). Claude 기준 아님
동시 처리량 4.2배, 하루 $50.40→$2.70근거 없음코드·ADR·문서 어디에도 측정 없음(하루 금액은 단가×3,000단계 어림)
