# ADR 쓰기

노션 '개발 워크플로우'의 4단계(설계)를 돕는 절차입니다. 기준은 [docs/adr/README.md](../../../docs/adr/README.md), 형식은 [docs/templates/adr.md](../../../docs/templates/adr.md)입니다.

## 1. ADR 대상인지 판단

`docs/adr/README.md`의 '무엇을 ADR로 남기나'로 판단합니다.

- 대상이면 계속합니다.
- 기획·범위·판단 기준·팀 운영 규칙이면 ADR이 아니라 노션 결정 로그 항목 초안을 씁니다.
- 이슈 안에서 끝나는 구현 세부면 PR 본문에 적으면 된다고 알려 주고 멈춥니다.

## 2. 읽을 것

- `docs/adr/` 목록과 관련 ADR. 채택된 ADR과 다른 결정이면 새 ADR이 이전 ADR을 대체하는 것이고, 사람에게 먼저 확인받아야 합니다.
- 관련 코드, `docs/api-spec.md`, `docs/erd.md`, 노션 결정 로그·기능 기획서(있으면).

## 3. 쓰는 법

- 파일: `docs/adr/{다음 번호 4자리}-{짧은-영문-이름}.md`. 번호는 `docs/adr/README.md` 목록의 다음 번호입니다.
- 템플릿의 절(맥락, 결정, 검토한 다른 방법, 결과, 다시 볼 때)을 모두 채웁니다.
  - 맥락: 그때의 제약(일정, 인원, 외부 API 한도, 규칙)과 확인한 사실만.
  - 결정: "~한다"로, 코드의 어디에 반영되는지(파일·클래스·상수)까지.
  - 검토한 다른 방법: 실제로 고려한 방법을 최소 2개, 고르지 않은 이유와 함께. 허수아비 대안을 만들지 않습니다.
  - 결과: 좋아지는 점, 감수하는 점, 지켜야 할 것.
- 이미 있는 코드를 기록하는 경우, 클래스·상수·설정 이름과 값을 코드에서 직접 확인하고 씁니다. 확인하지 못한 내용은 쓰지 않습니다.
- 상태: 구현 PR에 함께 넣으면 '채택', 구현 전에 합의가 필요하면 '제안'.
- 이전 ADR을 대체하면 이전 ADR은 상태 줄만 '대체됨(ADR-NNNN)'으로 바꿉니다. 결정 내용은 고치지 않습니다. 예외로, 이미 있는 코드를 소급 기록한 ADR이 코드와 다르게 적혀 있으면 코드에 맞춰 고칩니다.
- 다른 열린 PR이 같은 번호를 쓰고 있으면 나중에 병합되는 쪽이 번호를 올립니다.
- `docs/adr/README.md` 목록에 한 줄을 더합니다. 제목은 ADR의 H1과 똑같이 씁니다.

## 4. 내보내기

- 파일을 만들거나 고치고, 바뀐 파일과 '사람이 확인할 것'(대안과 이유가 맞는지, 대체 여부)을 알려 줍니다.
- 커밋·PR은 사용자가 요청할 때만 합니다. PR 본문의 'ADR' 항목에 번호를 적습니다.
