# 기능 기획서를 이슈로 쪼개기

노션 '개발 워크플로우'의 5단계(WBS·이슈)를 돕는 절차입니다. 결과는 이슈 **초안 목록**입니다. GitHub에 실제로 만드는 것은 사용자가 요청할 때만 합니다.

## 먼저 확인할 것

1. 기획서를 읽습니다(노션 링크, 붙여 넣은 내용, 또는 FS 번호로 [기능 기획서 DB](https://app.notion.com/p/e1f20d0ae0584b6ba85e2b80906814d1)에서 찾기). 상태가 '확정'이 아니면 쪼개지 않고, 무엇이 비어서 확정이 안 됐는지 알려 줍니다.
2. 저장소 `AGENTS.md`, 이슈 템플릿 `.github/ISSUE_TEMPLATE/task.md`, 관련 ADR·`docs/api-spec.md`·`docs/erd.md`를 읽습니다.
3. 이미 있는 이슈를 확인합니다(`gh issue list --state all --limit 200`. GraphQL이 막힌 환경이면 `gh api "repos/ShinhanDSProject/dart-insight/issues?state=all&per_page=100"`). 같은 일을 하는 이슈가 있으면 새로 만들지 않고 그 이슈를 기획서에 연결하자고 제안합니다.

## 쪼개는 법

- 이슈 하나는 한 사람이 1~3일에 끝낼 수 있고, PR 하나로 검토할 수 있는 크기입니다. 보통 서비스·역할(frontend, backend, ai, data)을 따라 나눕니다.
- API·DB가 바뀌면 그 문서·마이그레이션 작업을 앞선 이슈로 두고 나머지 이슈의 선행으로 겁니다.
- **WBS ID**: 기능이 속한 그룹의 다음 번호를 씁니다. 그룹은 0 기반, 1 기업·공시 조회, 2 비교 분석, 3 결과·근거, 4 데이터(OpenDART·원문), 5 검토·표현 검사·표시, 6 확장(로그인·즐겨찾기·알림), 7 검증·발표입니다. 기존 이슈 제목에서 그룹의 마지막 번호를 확인합니다. 이미 있는 이슈의 후속·버그는 새 번호 대신 원래 WBS ID를 씁니다(예: 2.3의 버그는 `2.3 [Compare] …`). 그룹이 애매하면 사용자에게 묻습니다.
- **제목**: `{WBS ID} [영역] 동작 + 대상` (예: `2.8 [Compare] 주석 표 변경 탐지`). 영역은 기존 이슈에서 쓰는 이름을 따릅니다(예: Company, Disclosure, Compare, Results, Evidence, Data, Compliance, AI, Backend, Frontend, Infra, Design, Test, Docs).
- **본문**: 이슈 템플릿 순서를 지킵니다.
  - 관련 기획서: `FS-n` 링크와 이 이슈가 다루는 AC 번호
  - 완료 기준: 다루는 AC를 이슈 수준으로 옮겨 적고, 필요한 기술 기준(문서 갱신, 테스트, 마이그레이션)을 더합니다. AC에 없는 기능을 끼워 넣지 않습니다.
  - 선행 이슈, 관련 결정, 관련 화면(W-ID)
- **레이블**: 작업 종류(feature·backend·frontend·data·ai·infra·test·docs, 버그는 bug) + 우선순위(P1·P2·보류). 마일스톤은 P1 이슈에만 기획서의 마일스톤을 붙이고, P2·보류는 비워 둡니다. 미결정 항목이 걸려 있으면 `decision-needed`.
- 모든 AC가 적어도 한 이슈에 들어갔는지 표로 확인합니다. 빠진 AC가 있으면 알려 줍니다.

## 내보내기

1. 먼저 표로 보여 줍니다: WBS ID · 제목 · 영역 · 다루는 AC · 선행 · 레이블. 이어서 이슈마다 본문 초안.
2. 사용자가 만들어 달라고 하면 선행 순서대로 `gh issue create`(또는 GitHub API)로 만들고, 만든 번호로 선행 링크를 채웁니다.
3. 기획서 10절(작업 쪼개기) 표와 'GitHub 이슈' 속성에 넣을 내용을 알려 줍니다. 노션 도구가 있고 사용자가 원하면 직접 채웁니다.
4. 담당자(Assignees)는 사람이 정합니다. 추측해서 넣지 않습니다.
