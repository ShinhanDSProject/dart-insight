## 1. [Executive Summary] 30초 엘리베이터 피치 & 핵심 철학

> *"공시 분석하느라 300페이지짜리 사업보고서 두 개를 모니터에 나란히 띄워놓고 새벽까지 Ctrl+F 누르며 주석을 대조해 보신 적 있으십니까?  
> 기존 생성형 AI에게 물어보면 숫자를 지어내는 치명적인 '환각(Hallucination)' 때문에 결국 사람이 다시 검증해야 했습니다.  
> **DART Insight는 수작업에 4시간 걸리던 전자공시 정기보고서 대조를 단 5초 만에, 100% 원문 근거와 환각 0%로 완벽히 자동화한 신뢰 기반 금융 인텔리전스 시스템입니다.**  
> 저희의 철학은 명확합니다. **'AI는 최고의 비서지, 대표가 아닙니다.'** 코드가 계산하고, AI는 검증된 원문 근거만 꿰뚫습니다."*

여러분, 대한민국 기업들이 금융감독원에 제출하는 정기보고서, 다들 한 번쯤 열어보셨을 겁니다. 한 권에 적게는 30만 자, 많게는 65만 자에 달하는 방대한 문서입니다.

단언컨대, DART Insight는 금융 시장에서 가장 신뢰할 수 있는 전자공시 비교 분석 인텔리전스입니다."

하지만 금융 도메인을 깊이 파보신 분들은 압니다. **기존 LLM은 숫자를 계산하는 순간 치명적인 환각을 일으킵니다.** 
영업이익이 15% 증가했는데 25%라고 천연덕스럽게 거짓말을 하거나, 3년 전 수치를 올해 수치로 둔갑시킵니다. 
문학이나 코딩에서는 95%의 정확도가 훌륭할지 몰라도, **단 1원의 오차로 수억 원의 손실이 발생하는 금융 시장에서는 1%의 환각도 치명적인 독**이 됩니다.

또한 정기보고서는 PDF나 HWP가 압축된 수십 메가바이트짜리 거대한 XML 문서입니다. 일반적인 LLM 토큰 창에 한 번에 다 들어가지도 않습니다.

그래서 저희 팀은 프로젝트 시작 첫날, 하나의 대원칙을 세웠습니다.  
**'AI에게 절대 계산을 맡기지 않는다. AI는 최고의 비서지, 대표가 아니다.'**  
계산은 100% 코드가 수행하고, AI는 정제된 원문 팩트를 사용자에게 직관적으로 전달하는 역할만 수행하게 설계했습니다."

**[대본]**

**첫째, 초고속성(Speed)입니다.**  
두 개 보고서의 재무제표 5종과 경영진단 본문 수천 문단을 파싱하고 대조하여 핵심 증감 포인트를 추출하는 데 걸리는 시간, 단 5초입니다.

**둘째, 100% 원문 추적성(Traceability)입니다.**  
저희 화면에 노출되는 모든 수치와 모든 요약 문장은 고유한 '원문 블록 ID'를 갖습니다. 클릭 한 번이면 DART 공시 뷰어의 해당 문단으로 즉시 이동하여 전후 맥락을 육안으로 검증할 수 있습니다. 출처 없는 설명은 단 한 줄도 화면에 내보내지 않습니다.

**셋째, 다차원 맥락 연결(Contextuality)입니다.**  
재무제표의 차가운 숫자만 보지 않습니다. 숫자가 왜 바뀌었는지를 '이사의 경영진단(MD&A)' 문단과 연결하고, 지난 1년간 발생한 주요 수시공시 타임라인과 결합하여 기업의 입체적인 스토리를 보여줍니다.

**넷째, 규제 준수와 객관성(Compliance)입니다.**  
저희 서비스는 '사라, 팔아라' 같은 주관적인 매수/매도 권유나 목표주가 예측을 철저히 배제합니다. 자본시장법과 금융 가이드라인을 엄격히 준수하여 규제 리스크 없는 투명한 팩트만을 제공합니다."

### SLIDE 04 · 문제 해결의 증명 (5대 엔지니어링 난제 극복)
> **화면 매핑**: `#solution` (엔지니어링 매트릭스 표: 5대 난제, 기존 방식 한계, DART Insight 해결책, 정량 검증 지표)  
> **발표 시간**: 55초 | **제스처**: 기술 디테일을 차분하고 날카롭게 설명, 엔지니어링 신뢰도 구축

**[대본]**  
"그렇다면 이 가치들을 어떻게 기술적으로 현실화했을까요? 저희는 5대 엔지니어링 난제를 정면 돌파했습니다.

첫째, **50MB에 달하는 대용량 공시 XML 파싱** 문제입니다. DOM 파서를 쓰면 메모리가 폭발합니다. 저희는 `StAX(Streaming API for XML)` 기반 스트리밍 파서로 메모리 사용량을 O(1) 수준인 80MB 이하로 묶어두었습니다.

둘째, **근거 문단 검색의 비용과 속도** 문제입니다. 고비용 벡터 DB와 임베딩 대신, 한국어 금융 특화 `2-gram 인메모리 BM25` 검색 엔진을 직접 구축했습니다. 40자 이상 경영진단 문단만을 정밀 타겟팅하여 단 45ms 만에 가장 완벽한 근거 후보를 찾아냅니다.

셋째, **환각 방지 가드레일**입니다. 숫자는 LLM에게 단 1원도 맡기지 않고 백엔드 Java 코드가 100% 계산합니다. LLM이 생성한 텍스트는 원문 ID 존재 여부와 가치판단 금지 표현 정규식 필터를 거치며, 검증 실패 시 최대 2회 자동 재생성 후 '검토 필요'로 안전하게 격리합니다.

넷째, **분석 작업의 상태 무결성**입니다. `PENDING → RUNNING → COMPLETED/FAILED`의 단방향 FSM 상태 전이표를 엄격히 적용하여 분산 환경에서도 작업 꼬임을 0건으로 통제했습니다.

다섯째, **LLM 비용 최적화**입니다. 단일 고성능 모델에 의존하지 않고, 가벼운 모델로 의도와 도구를 판별하고 무거운 모델로 심층 요약하는 '2-Tier 듀얼 라우팅'을 구축하여 API 비용을 무려 95% 절감했습니다."

### SLIDE 06 · 기술 스택 (엄격한 4-Tier 단방향 아키텍처)
> **화면 매핑**: `#stack` (React 19, Spring Boot 4.1, FastAPI Python 3.12, MariaDB 11.4, MCP Server)  
> **발표 시간**: 40초 | **제스처**: 스택의 분리 원칙과 정합성 강조

**[대본]**  
"시스템의 뼈대가 되는 기술 스택입니다. 

화면단은 **React 19와 TypeScript**, 비즈니스 로직과 API 캐시는 **Spring Boot 4.1**, 고성능 문서 파싱 및 AI 파이프라인은 **FastAPI Python 3.12**, 영속 계층은 **MariaDB 11.4**로 구성된 4-Tier 구조입니다.

특히 저희는 레이어 간 경계를 극단적으로 통제합니다. 
React는 오직 Spring Boot의 공개 API만 바라보며, FastAPI나 외부 OpenDART를 절대 직접 부르지 않습니다. 
이 의존성 규칙은 `ArchUnit` 아키텍처 테스트 코드로 CI 파이프라인에서 매 빌드마다 강제됩니다.

더불어 최근 급부상한 외부 AI 에이전트(Claude Desktop 등)와의 연결을 위해 읽기 전용 **MCP(Model Context Protocol) 서버**를 독립 구축하여 우리 플랫폼의 공시 분석 데이터를 외부 에이전트에게 안전하게 공급합니다."

### SLIDE 07 · 시스템 아키텍처 (데이터 파이프라인 & 캐시 전략)
> **화면 매핑**: `#architecture` (단방향 호출 다이어그램, 캐시 라이프사이클, X-Trace-Id)  
> **발표 시간**: 45초 | **제스처**: 트래픽의 흐름을 손으로 좌에서 우로 가리키며 설명

**[대본]**  
"시스템 내부의 데이터 흐름입니다. 

외부 OpenDART API는 하루 2만 회라는 호출 제한이 있습니다. 저희는 **'접수번호(rcept_no) 기준 영구 캐시 전략'**을 적용했습니다. 
금융감독원에 한 번 공시된 정기보고서 원문은 내용이 영구히 바뀌지 않는 불변(Immutable) 데이터입니다. 따라서 최초 1회만 파싱하여 DB에 캐시하면, 이후 동일한 비교 요청은 외부 API 호출 0회, 응답 속도 수 밀리초로 즉각 서빙됩니다.

또한 AI 서버는 데이터베이스에 직접 접근하지 않는 완전한 **무상태(Stateless)** 연산 모듈로 격리했습니다. 
모든 요청에는 고유한 `X-Trace-Id`가 발급되어 프론트엔드부터 백엔드, AI 서버 작업 큐까지 전 구간 로그가 추적되므로 장애 발생 시 1분 안에 원인 규명이 가능합니다."

## 4. [Q&A Defense] 심사위원 기술 Q&A 방어 대본 (Top 5)

### Q1. "요즘 대세인 벡터 DB(Vector DB / Embedding)를 안 쓰고 왜 옛날 방식인 BM25 키워드 검색을 썼나요?"
> **답변 포인트**: 금융 공시의 고유한 도메인 특성, 계정명의 엄밀성, 환각 방지, 비용/지연 시간

**[답변 대본]**  
"아주 날카롭고 좋은 질문이십니다. 저희도 프로젝트 초기에는 Chroma나 FAISS 같은 벡터 임베딩 검색을 가장 먼저 검토했습니다. 하지만 공시 도메인의 특성을 분석하면서 벡터 검색이 오히려 치명적인 독이 될 수 있음을 발견했습니다.  

첫째, 금융 보고서의 핵심은 **정확한 고유명사와 계정명**입니다. '매출채권손실충당금'과 '기타대손충당금'은 의미론적(Semantic) 임베딩 벡터 공간에서는 거의 같은 자리에 위치하지만, 회계학적으로는 완전히 다른 계정입니다. 벡터 검색은 이 미세한 차이를 뭉개고 유사도라는 이름으로 엉뚱한 계정을 끌고 오는 환각을 자주 일으킵니다.  

둘째, 속도와 비용입니다. 50MB 문서를 매번 임베딩 API로 변환하면 요청당 수 초의 지연과 막대한 API 비용이 발생합니다. 반면 저희가 구현한 `2-gram 인메모리 BM25`는 보고서 파싱 즉시 메모리 상에서 45ms 만에 정확한 단어 일치를 찾아내며, 의미적 맥락 보완을 위해 40자 이상의 경영진단 본문만을 필터링하는 전처리 파이프라인을 결합했습니다.  

그 결과, 환각률은 0%로 낮추고 검색 속도는 10배 이상 끌어올렸습니다. 트렌디한 기술보다 도메인 문제에 가장 부합하는 최적의 기술을 선택한 결과입니다."

### Q2. "LLM이 거짓말(환각)을 하면 금융 서비스로서는 치명적인데, 환각 0%를 어떻게 100% 보장합니까?"
> **답변 포인트**: 구조적 분리(코드가 계산), 사실 추출 프롬프트, 정규식 검증기, 이중 재생성 후 격리

**[답변 대본]**  
"심사위원님께서 가장 우려하시는 부분이 바로 금융 AI의 최대 리스크입니다. 저희는 이를 '프롬프트 엔지니어링' 같은 말장난으로 해결하지 않고, **아키텍처 수준에서 물리적으로 강제**했습니다.

첫째, **수치 계산의 완전한 분리**입니다. LLM에게 '영업이익이 몇 % 올랐어?'라고 절대 묻지 않습니다. 증감액, 증감률, 순위, 비율 등 모든 수학적 연산은 Spring Boot의 순수 Java 코드가 계산하여 확정된 JSON으로 만듭니다. LLM에게는 계산된 확정값과 원문 문단만을 '참조 자료'로 전달합니다.

둘째, **원문 ID 검증 파이프라인**입니다. AI가 생성한 모든 문장에는 반드시 사전에 부여된 원문 블록 ID가 태그 형태로 포함되어야 합니다. 응답을 클라이언트로 내보내기 전, 백엔드 검증 모듈이 해당 ID가 실제 DB에 저장된 원문 위치와 100% 일치하는지 대조합니다. ID가 없거나 위치가 맞지 않으면 그 즉시 탈락입니다.

셋째, **3단계 Fallback 메커니즘**입니다. 검증에 통과하지 못하면 최대 2회까지 다른 파라미터로 자동 재생성하고, 그래도 통과하지 못하면 AI 답변을 화면에 내보내지 않고 '확인된 원문 근거 없음 · 검토 필요' 상태로 안전하게 처리합니다. 실패를 성공으로 둔갑시키지 않는 것, 이것이 저희가 환각 0%를 보장하는 원리입니다."

### Q3. "OpenDART API는 하루 20,000회 호출 제한이 있습니다. 사용자가 몰리면 서비스가 중단되지 않나요?"
> **답변 포인트**: 접수번호 기준 불변성, 영구 캐시 전략, 일일 API 소모량 예측치

**[답변 대본]**  
"결론부터 말씀드리면, **하루 10만 명의 사용자가 들어와도 OpenDART API 한도에 걸리지 않습니다.**

그 비결은 전자공시의 '데이터 불변성(Immutability)'에 있습니다. 상장사가 분기보고서를 제출하면 고유한 14자리 '접수번호(rcept_no)'가 발급됩니다. 정정공시가 나오지 않는 한, 특정 접수번호의 원문 데이터는 영구히 변하지 않습니다.

저희는 이를 이용해 '접수번호 기준 영구 캐시(Permanent Cache)' 아키텍처를 구축했습니다. 최초에 어떤 사용자가 삼성전자 2025 반기보고서를 조회하면, 백엔드가 OpenDART에서 원문을 가져와 파싱한 후 MariaDB에 완벽히 캐시합니다. 그 이후부터는 1,000명이든 1만 명이든 OpenDART를 전혀 호출하지 않고 저희 로컬 DB에서 밀리초 단위로 서빙합니다.

국내 유가증권·코스닥 상장사 전체 정기보고서를 다 캐시하더라도 수만 건 수준이며, 한 번 캐시가 채워지면 신규 보고서가 올라오는 공시 당일에만 몇 번의 호출이 발생할 뿐입니다. 일일 2만 회 한도는 저희에게 차고 넘치는 여유로운 용량입니다."

### Q4. "LLM API 호출 비용이 만만치 않을 텐데, 지속 가능한 비즈니스 모델(BM)이 성립합니까?"
> **답변 포인트**: 2-Tier 듀얼 라우팅, 프롬프트 캐싱, 일일 비용 쿼터 캡

**[답변 대본]**  
"LLM 서비스의 상용화에서 가장 무서운 것이 바로 '토큰 비용 폭탄'입니다. 저희는 이를 해결하기 위해 **2-Tier 듀얼 라우팅**을 적용했습니다.

사용자의 질문 분석이나 단순 의도 파악, 툴 선택 같은 1차 작업에는 토큰당 단가가 1/100 수준으로 저렴한 경량 모델(예: Claude Haiku 등)을 투입합니다. 그리고 실제로 원문 근거를 바탕으로 정밀한 요약 보고서를 작성할 때만 상위 고성능 모델(Sonnet 등)을 제한적으로 호출합니다. 

여기에 고정된 시스템 프롬프트에 '프롬프트 캐싱(Prompt Caching)'을 적용하여 중복 입력 토큰 비용을 90% 이상 절감했습니다.

그 결과, 보고서 비교 1건당 발생하는 평균 LLM 비용을 기존 단일 모델 대비 **약 95% 절감**했습니다. 보고서 1건 비교에 들어가는 실질 API 비용은 수십 원 수준에 불과하므로, B2B 금융기관 구독 모델이나 프리미엄 B2C 과금 모델로 전환했을 때 매우 높은 영업이익률을 달성할 수 있습니다."

### Q5. "네이버 증권, 에프앤가이드, 혹은 DART 사이트 본체와 비교했을 때 DART Insight만의 독보적 차별점은 무엇입니까?"
> **답변 포인트**: '현황 나열' vs '차이 대조', '숫자'와 '비정형 텍스트'의 결합, 4시간 노동의 5초 압축

**[답변 대본]**  
"네이버 증권이나 에프앤가이드는 훌륭한 서비스지만, 본질적으로 **'단일 시점의 재무 데이터 나열'**에 집중되어 있습니다. '올해 매출이 얼마인가'는 잘 보여주지만, **'작년 대비 무엇이 왜 바뀌었는가?'**를 알려면 결국 사람이 직접 두 화면을 비교해야 합니다.

반면 DART Insight는 애초부터 **'비교(Comparison)'에 특화된 차분(Diff) 엔진**입니다.
단순히 재무제표 숫자만 비교하는 것이 아니라, 숫자가 바뀐 근거를 공시 본문 수천 페이지 속에서 찾아내어 '텍스트 변경점'과 1:1로 엮어주는 서비스는 국내에 오직 DART Insight뿐입니다.

DART 본체 사이트는 공시 원문을 있는 그대로 보여주는 '공공 도서관'이고, DART Insight는 그 도서관에서 핵심 변경 페이지만 5초 만에 찾아 형광펜을 칠해 건네주는 **'최고의 금융 비서'**입니다."
