# ADR-0047: 문장 변경의 목록 분류와 표 행 비교는 ai-server가 비교할 때 정하고, backend가 변경과 함께 저장한다

- 상태: 채택
- 결정한 날: 2026-11-03
- 관련: 이슈 2.9, 기능 기획서 '문장 변화 탭 목록 정리'(FS 번호는 등록 후 채움), [ADR-0021](0021-numeric-update-and-moved-text-changes.md), [ADR-0014](0014-analysis-reuse-and-version.md), [ADR-0011](0011-jdbc-batch-for-large-tables.md), `ai-server/app/compare/`, `TextComparisonService`, `TextChangeStore`

## 맥락

- 로컬 고려아연 분석(`m2-9`)의 문장 변경은 2,677건이고, 2,236건(84%)이 표, 1,899건(71%)이 주석 변경입니다. 제목 줄이 과징금 문단보다 먼저 나옵니다.
- 표 구성이 바뀌면 유사도가 낮아 `text_diff.py`가 같은 소송 표를 `DELETED`와 `ADDED` 두 건으로 잡습니다. 고려아연 소송 표는 행으로 비교하면 바뀜 2, 새로 3, 이번엔 없음 11, 그대로 1입니다.
- 화면은 잡음과 주석을 접고, 남은 변경을 분야로 나눠 보여 주려고 합니다. 잡음과 분야 판정은 전체 글과 섹션 경로를 봐야 합니다.
- 목록의 거르기, 건수, 쪽 나누기는 `TextChangeStore`의 SQL이 합니다. 분류를 저장하지 않으면 SQL로 거르거나 셀 수 없습니다.
- `search_text_changes`(채팅)가 같은 목록 조회를 쓰므로, 파라미터가 없는 조회의 결과가 달라지면 채팅이 주석을 찾지 못합니다.
- 변경의 종류와 우선순위 점수를 바꾸면 요약 선택(`SummarySelector`)과 문장 변경 이력([ADR-0028](0028-text-change-history-from-completed-analyses.md))까지 영향을 받습니다. 이번 일은 LLM과 점수 변경 없이 합니다.

## 결정

- 분류와 표 행 비교는 ai-server의 비교 단계가 LLM 없이 규칙으로 합니다. 새 모듈 `ai-server/app/compare/listing.py`에 두고, 결과를 `POST /internal/text-changes` 응답에 더합니다.
- 규칙 버전은 새 상수 `LIST_VERSION`(`text-list-1`)입니다. `change_type`, 위치, 우선순위 점수를 바꾸지 않으므로 `DIFF_VERSION`과 `PRIORITY_VERSION`은 그대로 둡니다.
- backend는 받은 값을 변경과 함께 저장합니다. 저장 구조와 응답 필드는 `docs/erd.md`와 `docs/api-spec.md`에 있습니다.
- 변경 하나는 목록 묶음 하나에만 속합니다. 분야는 기본 목록(`MAIN`)의 변경에만 있습니다.
- 표 행 비교는 지금 보내는 블록 글(줄이 행, ` | `가 칸)로 합니다. 표 안에서 값이 겹치지 않는 공통 열 중 양쪽에 함께 있는 값이 가장 많은 열로 짝짓습니다. 금액처럼 숫자뿐인 열은 우연히 같은 값으로 잘못 짝지어지므로 쓰지 않습니다. 고려아연 소송 표에서는 이 규칙으로 `사건의 명칭(사건번호)` 열이 골라지고 위 건수가 나옵니다. 칸 수가 맞지 않거나 짝지을 열을 정할 수 없으면 짝을 추측하지 않고 `NOT_COMPARED`로 둡니다.
- 구성이 바뀐 표는 `DELETED`와 `ADDED` 두 행을 그대로 남깁니다. 같은 섹션에서 행 비교가 된 쌍이면 `ADDED` 행에 비교 결과와 이전 표의 위치를 두고, `DELETED` 행은 `PAIRED_TABLE`로 접어 한 표가 목록에 두 번 나오지 않게 합니다.
- 짝은 같은 섹션에서 머리글(첫 행)이 같고 짝지을 열이 있는 삭제·추가 표끼리만 만듭니다. 짝지을 열에서 양쪽에 함께 있는 값이 가장 많은 쌍부터 정하고, 같으면 이전 표, 현재 표의 문서 순서가 앞선 쌍을 먼저 정합니다. 표 하나는 한 쌍에만 들어가고, 짝이 없는 표는 `DELETED`·`ADDED` 그대로 둡니다.
- 목록 API의 새 값은 응답에 더하기만 합니다. `group`, `field` 파라미터가 없으면 지금과 같은 변경을 같은 순서로 돌려줍니다. 옛 분석은 화면이 첫 응답을 받기 전에는 옛 분석인지 모르므로, 두 파라미터를 무시하고 모든 변경을 돌려줍니다.
- 결과가 달라지므로 분류를 저장하는 backend PR에서 `Analysis.CURRENT_VERSION`을 올립니다([ADR-0014](0014-analysis-reuse-and-version.md)). ai-server PR은 응답 필드를 더하기만 하고, backend는 모르는 필드를 무시하므로 먼저 병합해도 저장 결과가 달라지지 않습니다.
- 응답에 `listVersion`이 없으면 backend는 문장 비교를 실패로 끝냅니다. 실패한 결과는 다시 쓰지 않으므로, 옛 ai-server와 새 backend가 함께 돌아도 분류 없는 결과가 새 버전으로 남지 않습니다. 배포는 ai-server를 먼저 합니다.
- 옛 분석의 행은 채우지 않습니다. `list_version`이 null이면 옛 분석이고, 화면은 표와 묶음 없이 저장된 변경을 지금처럼 보여 줍니다.
- 원문 비교 창의 `tableDiff.ts`는 이번에 바꾸지 않습니다. 화면 강조용으로 두고, 저장된 행 비교와 기준을 맞추는 일은 필요해질 때 합니다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 조회할 때마다 계산(`RiskSections`처럼) | 위험 관련 판정은 섹션 경로만 보면 되지만, 잡음과 주석 예외는 전체 글을 봐야 합니다. 쪽 하나를 보여 주려고 분석의 모든 글을 읽어야 하고, SQL로 거르거나 셀 수 없습니다. |
| backend가 저장할 때 분류 | 글과 섹션 경로가 있어 가능하지만, 숫자 가리기와 띄어쓰기 비교(`mask_numbers`, `formatting_only_differs`), 섹션 트리가 ai-server에 있어 규칙이 두 서비스로 나뉩니다. |
| 화면에서 분류 | 목록 응답에는 앞부분 240자 미리보기만 있고 쪽 단위로 받으므로, 전체 건수를 알 수 없습니다. |
| 구성이 바뀐 표를 `MODIFIED` 한 건으로 합치기 | 한 건으로 보여 주기는 깔끔하지만, 변경 건수, 우선순위 점수(추가·삭제 +20, 수정 +10), 요약 선택, 이력이 함께 달라져 이번 범위를 넘습니다. |
| 행 비교에 표 셀 JSON을 함께 보내기 | 머리글 칸을 알 수 있어 더 정확하지만, 이미 큰 요청이 더 커집니다. 글로 비교할 수 있는지 먼저 보고, 부족하면 바꿉니다. |
| 옛 분석을 일괄 재계산 | 원문을 다시 비교해야 하고, 규칙이 바뀔 때마다 반복됩니다. 다시 분석 안내([#298](https://github.com/ShinhanDSProject/dart-insight/issues/298))가 이미 있습니다. |

## 결과

- 좋아지는 점: 분류를 SQL로 거르고 셀 수 있어 쪽 나누기와 건수가 맞습니다. 변경 종류, 점수, 요약 선택, 이력, 채팅 조회의 동작이 그대로입니다. 접은 변경도 지우지 않습니다.
- 감수하는 점: 버전을 올리면 그 뒤의 요청은 처음부터 다시 분석해 비용과 시간이 듭니다. 분류를 고칠 때마다 버전을 올려야 합니다. `row_diff` 때문에 저장량이 늘어납니다. 카드의 행 비교와 원문 비교 창의 강조가 다르게 보일 수 있습니다. 분류 규칙(제목 줄 길이, 주석 예외 낱말, 분야 경로)은 잠정이고, 잘못 접힌 변경은 묶음을 열어야 보입니다.
- 지켜야 할 것: 분류 결과가 달라지게 규칙을 바꾸면 `LIST_VERSION`과 `Analysis.CURRENT_VERSION`을 함께 올립니다. 표 짝짓기는 삭제·추가 표가 여럿인 섹션을 테스트합니다. `group`, `field`가 없는 조회의 결과를 바꾸지 않습니다. 짝을 정하지 못한 항목(`UNPAIRED`)은 접지 않습니다. 행 비교 화면에 '사라짐'이라고 쓰지 않습니다.

## 다시 볼 때

- 세 기업 이상의 실제 원문에서 잘못 접힌 변경이나 잘못 짝지은 표가 나올 때
- 정답 자료(7.5)로 분류와 행 비교의 정확도를 잴 수 있을 때
- 구성이 바뀐 표를 한 건으로 합치거나, 행 비교 결과로 우선순위 점수를 바꾸고 싶을 때
- 사건 묶기(2단계)가 묶음이나 분야 값을 다르게 필요로 할 때
