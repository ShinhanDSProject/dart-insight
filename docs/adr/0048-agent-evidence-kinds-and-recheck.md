# ADR-0048: 에이전트 채팅의 근거는 7가지 종류로 두고, backend는 근거 ID가 이 채팅에서 저장된 자료로 만든 근거 표에 있는지 다시 확인한다

- 상태: 채택
- 결정한 날: 2026-11-04
- 관련: #582, PR #630, [ADR-0044](0044-agent-tools-run-in-backend.md), [ADR-0045](0045-langgraph-agent-step-graph.md), `docs/api-spec.md` 채팅 API `citations`

## 맥락

- ADR-0044는 "backend는 응답 전에 근거 ID가 실제 저장된 원문 위치인지 한 번 더 확인한다"고 정했다.
- #577부터 코드는 원문 위치(`{접수번호}#B{블록}`·`{접수번호}#S{항목}`)가 아닌 근거도 받는다: 문장 변경 `T{changeId}`, 재무 계정 변화 `F{changeId}`, 수시공시 `D{접수번호}`. 다시 확인도 원문 위치 조회가 아니라, Tool을 실행하며 backend가 저장된 자료로 만든 근거 표(`AgentChatService`의 `evidence`)에 그 ID가 있는지로 해 왔다(`ChatResults.finalAnswer`의 `AnswerMarkers.convert(..., evidence.keySet(), ...)`).
- #582는 기업 화면의 값을 근거로 쓰려고 두 종류를 더한다. 보고서 값(최대주주 지분율, 재무 추이 금액, 체크 포인트 값, 수시공시 주요정보)과 기업(개황, 기업 검색 후보)이다. 이 값들은 원문 문단이 아니라 기존 API가 OpenDART 응답으로 만든 값이고, 값마다 저장된 위치 번호가 없다.
- 그래서 ADR-0044의 '저장된 원문 위치'라는 문장이 실제 동작과 어긋난다. 채택된 ADR의 결정 내용은 고치지 않으므로, 근거 종류와 다시 확인의 뜻을 이 ADR로 구체화한다.

## 결정

- 에이전트 채팅의 근거는 아래 7가지 종류로 둔다(`backend/.../agent/domain/Evidence.java`의 `Kind`). 화면에 보내는 위치 필드는 `docs/api-spec.md` 채팅 API `citations` 표를 따른다.

  | 종류 | 근거 ID | 가리키는 것 | 만드는 곳 |
  | --- | --- | --- | --- |
  | `BLOCK` | `{접수번호}#B{블록 번호}` | 저장된 원문 문단·표(`document_block`) | `Evidence.block` |
  | `SECTION` | `{접수번호}#S{항목 번호}` | 저장된 원문 목차 항목 | `Evidence.section` |
  | `TEXT_CHANGE` | `T{changeId}` | 이 분석의 문장 변경 | `Evidence.textChange` |
  | `FINANCIAL_CHANGE` | `F{changeId}` | 이 분석의 재무 계정 변화(코드가 계산한 값) | `Evidence.financialChange` |
  | `DISCLOSURE` | `D{접수번호}` | 수시공시·공시 목록의 공시 한 건(보조 근거) | `Evidence.disclosure` |
  | `REPORT_VALUE` | `{접수번호}#V{n}` | 기업 화면 API가 준 보고서 값 하나. 접수번호는 값의 근거 접수번호(`sourceRceptNo` 우선) | `Evidence.reportValue` + `AgentChatService.numbered` |
  | `COMPANY` | `C{고유번호}` | 기업 하나(개황 또는 기업 검색 후보) | `Evidence.company` |

- `#V{n}`의 `n`은 저장된 위치가 아니라 **채팅 한 번 안에서** backend가 붙이는 번호다. 같은 값(접수번호·출처·항목·값이 같음)을 다시 조회하면 같은 번호를 쓴다(`Evidence.valueKey`). 다른 채팅에서는 같은 번호가 다른 값을 가리킬 수 있으므로, 채팅 밖(노트·질문 기록 등)에 `#V` ID를 저장하거나 다시 쓰지 않는다.
- backend의 다시 확인(ADR-0044)은 "최종 답의 근거 ID가 이 채팅에서 실행에 성공한 Tool 결과로 backend가 저장된 자료를 읽어 만든 근거 표에 있는가"이다. 7가지 종류 모두 같은 방법으로 확인한다. 하나라도 없으면 답을 버리고 '검토 필요'로 끝낸다(ADR-0044와 같음). 원문 위치(`#B`·`#S`)는 근거 표를 만들 때 저장된 원문에서 읽어 만들고, 나머지 종류는 저장된 분석 결과·기업 화면 서비스의 결과에서 만든다. LLM이 만든 글로 근거를 만들지 않는다.
- 답의 숫자 검사(ai-server `app/llm/grounding.py`)는 종류와 상관없이 그 문장이 인용한 Tool 결과 줄의 글로 한다. 그래서 보고서 값 줄의 글에는 API가 준 값을 그대로 넣는다(`AgentCompanyTools`).

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 보고서 값도 저장된 위치 ID로 만들기(예: `key_fact` 테이블 행 ID) | 값을 주는 서비스가 여러 개(재무 추이·주요 사실·체크 포인트·주요정보)이고 행 구조가 서로 달라, 근거 ID를 위해 테이블마다 키 규칙을 새로 정해야 한다. 채팅 근거는 응답 안에서만 쓰이므로 채팅 안 번호로 충분하다 |
| 보고서 값을 근거 없는 줄(`<item>`)로만 넘기기 | 답의 문장이 근거 표시를 가질 수 없어, "최대주주 바뀌었어?"(AC22)에 근거 칩을 붙일 수 없다. 숫자 검사에서도 인용한 근거가 없어 숫자를 쓸 수 없다 |
| ADR-0044를 대체하는 새 ADR로 다시 쓰기 | 바뀐 것은 다시 확인의 '무엇과 대조하나'라는 한 문장뿐이고, Tool을 backend가 실행한다는 결정은 그대로다. 대체하면 ADR-0044를 읽던 사람이 그대로인 부분까지 새 ADR에서 다시 찾아야 한다 |

## 결과

- 좋아지는 점: 근거 종류가 하나의 표로 정리되고, 다시 확인이 실제로 무엇과 대조하는지 문서와 코드가 같다. 기업 화면 값에도 근거 칩을 붙일 수 있다.
- 감수하는 점: `#V` ID는 채팅 밖에서 다시 가리킬 수 없다. 보고서 값의 근거 칩은 그 값을 준 보고서(접수번호·DART 링크)까지만 가리키고 문단 위치는 없다.
- 지켜야 할 것:
  - 새 근거 종류를 더하면 이 표와 `docs/api-spec.md` `citations` 표를 같은 PR에서 고친다.
  - 근거 표에는 저장된 자료로 만든 근거만 넣는다. LLM 답이나 AI 요약 문장을 근거 위치·미리보기로 쓰지 않는다.
  - `#V` ID는 채팅 응답 밖에 저장하지 않는다. 노트에 담을 대상이 되려면 저장된 위치를 가진 근거(재무·문장 변경, 답 인용)여야 한다.

## 다시 볼 때

- 노트·커뮤니티 글처럼 채팅 밖에서 보고서 값 근거를 다시 가리켜야 할 때(그때는 저장된 키가 필요함)
- 근거 질문(`analysis_question`)처럼 채팅 답 자체를 저장하게 될 때
