# ADR-0050: 주요 사건은 분석이 끝난 뒤 처음 열 때 별도 작업으로 만들고, backend가 실행·저장을 ai-server가 묶기·검증을 맡는다

- 상태: 채택(입력 범위와 입력 크기 가정은 ADR-0051이, 규모를 코드만 정한다는 부분은 ADR-0053이 대체)
- 결정한 날: 2026-11-04
- 관련: 이슈 #642(2.13), 후속 #643(2.14)·#644(2.15)·#645(2.16)·#646(3.36)·#649(7.7), 기능 기획서 초안 '문장 변화 탭 개편'(FS 번호는 등록 후 채움), [ADR-0014](0014-analysis-reuse-and-version.md), [ADR-0030](0030-related-disclosure-matching.md), [ADR-0042](0042-failed-llm-calls-in-response-header.md), [ADR-0047](0047-text-change-list-classification.md)

## 맥락

- 문장 변화 탭은 분야별 표까지 만들었지만 변경이 여전히 많습니다. 변경을 사건으로 묶는 일은 글을 읽어야 해서 LLM이 필요합니다.
- 기획서의 요구는 사건이 실패해도 분석은 `COMPLETED`이고 표와 전체 변경은 그대로 보이며(AC21), 표가 사건보다 먼저 보이는 것입니다(AC33). 지금 요약은 분석 작업 안에 있어 실패하면 분석이 `FAILED`가 되므로 이 요구와 맞지 않습니다.
- 관심 기업 자동 분석([ADR-0031](0031-favorite-report-auto-analysis-notification.md))과 시즌 순위([ADR-0037](0037-season-change-ranking.md))는 아무도 열어 보지 않을 분석도 만듭니다. 분석 작업 안에서 사건을 만들면 이 분석마다 비용이 듭니다.
- `SecurityConfig`는 분석 조회를 비로그인에도 엽니다. 사건을 만드는 요청도 비로그인으로 올 수 있어 호출 횟수를 서버가 막아야 합니다.
- 한 변경이 두 사건에 들어갈 수 있습니다. 예를 들어 유상증자 금액이 자금 조달 표와 다른 사건의 문단에 함께 있으면, 사건마다 세면 금액이 겹칩니다.
- **이슈 #642는 2.12 실험 결과를 근거로 쓰도록 했지만 이번에는 결과가 없습니다.** 담당자가 공용 키를 2단계 작업이 모두 끝난 뒤에 쓰기로 정했고(2026-11-04), 그 전에는 진짜 모델을 부르지 않습니다. 아래 '가정'은 모델 없이 잰 입력 크기만을 근거로 합니다.
- 잰 값(세 평가 보고서, 글 1,500자 제한, 토큰은 어림, 모델 호출 없음): 기본 목록 전체는 606~717건에 약 15~17만 토큰이고 사람이 꼽은 사건을 모두 담습니다. 후보 규칙(`UNPAIRED`, 주석에서 올림, 분야 `LITIGATION`·`CONTRACT`·`FUNDING`·`DIVIDEND`·`AUDIT`, 작성기준일 이후)을 쓰면 120~137건에 약 2.8~3.3만 토큰이고, 삼성전자에서 핵심 사건 5건 중 2건(대표이사 변경, 지분 인수)이 빠집니다.

## 결정

**언제:** 분석 작업 밖에서, 완료된 분석을 처음 열 때 시작하는 별도 비동기 작업으로 만든다. 자동으로 다시 시도하지 않는다.

**서비스 책임:**

- backend는 실행을 만들고 상태를 관리하고 결과를 저장한다. 자체 실행기(`TextEventRunner`)가 저장된 기본 목록(`list_group` `MAIN`·`UNPAIRED`)과 자본총계를 `POST /internal/text-events`로 보낸다. 외부 호출은 트랜잭션 밖에서 하고, 사건·연결·인용과 `COMPLETED` 전이는 한 트랜잭션으로 저장한다.
- ai-server(새 패키지 `app/events`)는 후보 고르기(규칙, 2.14), LLM 묶기와 인용·근거 검증, 표현 검사(2.15), 정렬(코드, 2.16)을 맡는다. LLM은 `LlmClient`로만 부른다. 규모와 순서는 코드가 정하고 LLM에 어림시키지 않는다.

**상태:** 실행 상태는 `PENDING → RUNNING → COMPLETED`·`FAILED`·`NOT_CREATED`로만 바뀌고, 코드에 허용 전이표를 둔다. 분석 상태 값에는 손대지 않는다. 아래 표에서 저장하지 않는 사유에 해당하면 실행이 없어도 `NOT_CREATED`로 답하고, 그 밖에 실행이 없으면 `NOT_STARTED`로 답한다.

| `NOT_CREATED` 사유 | 저장 | 다음 시작 요청 |
| --- | --- | --- |
| `DISABLED` 설정으로 꺼 둠 | 안 함 | 켜면 시작 |
| `OLD_ANALYSIS` 분류 전 분석(`list_version` null) | 안 함 | 만들지 않음 |
| `TEXT_COMPARE_FAILED` 문장 비교 실패 | 안 함 | 만들지 않음 |
| `FAKE_MODEL` 제공자가 fake | 함 | 새 실행 |
| `NO_CANDIDATES` 후보 변경 없음 | 함 | 같은 버전이면 그대로 |

**버전:** `Analysis.CURRENT_VERSION`을 올리지 않는다. 사건은 분석 결과 밖에 있으므로 관련 수시공시(ADR-0030)처럼 새 상수 `TextEvents.EVENT_VERSION`(`event-1`)을 실행 행에 저장한다. 후보 규칙, 프롬프트, 검증, 정렬이 바뀌면 이 상수를 올리고, 분석 버전은 올리지 않는다. 버전이 바뀌면 다음 시작 요청 때 새 실행을 만든다. 조회는 현재 버전의 실행만 보여 준다.

**옛 분석:** `list_version`이 null이면 만들지 않는다(재분석으로만 풀림). 그 밖의 옛 버전 분석은 재분석 없이 만들 수 있다.

**실패와 재시도:**

- LLM 출력은 스키마, 변경 번호, 인용과 원문의 글자 일치, 표현 검사로 검증한다. 실패하면 최대 2회 다시 만든다.
- 그래도 잘못된 사건은 내보내지 않고 건수(`droppedEventCount`)를 남긴다. 그 사건의 변경은 묶이지 않은 후보로 돌아간다. 남은 사건이 하나도 없으면 실행은 `FAILED`다.
- 끝난 뒤 실패(LLM을 쓸 수 없음, 시간 초과, 저장 실패, 서버 재시작으로 끊김, 실행 대기열이 가득 참)는 모두 `FAILED`이고 사건을 저장하지 않는다. 호출 기록은 ADR-0042대로 `X-Llm-Calls`로 받아 `llm_call`에 task `text_event`, `analysis_id`로 저장한다.
- 다시 시작은 사용자가 요청할 때만 한다. 비용을 막으려고 분석·버전마다 최근 24시간에 `FAILED` 3번이면 `429`로 거절한다. 검증 재생성 2회는 한 실행 안의 일이라 세지 않고, 대기열이 가득 차 끝난 실행은 LLM 비용이 없어 세지 않는다. 3번과 24시간은 측정 없이 정한 출발값이다.
- 동시 요청은 `(analysis_id, event_version, attempt_no)` 유니크로 막아 진행 중인 실행 하나만 남긴다.

**한 변경과 여러 사건:** 한 변경을 여러 사건에 묶을 수 있다. 사건마다 규모를 보여 주되 **사건끼리 규모를 더하지 않는다.** 분야 칸의 변경 건수는 변경 기준이라 영향이 없고, 칸의 사건 수는 칸마다 사건을 한 번만 센다.

**저장과 API:** `text_event_run`, `text_event`, `text_event_change`, `text_event_quote`, `text_event_unbound_change`를 새로 둔다(`docs/erd.md`). 많은 행은 `JdbcTemplate`으로 일괄 저장한다([ADR-0011](0011-jdbc-batch-for-large-tables.md)). 시작(`POST .../event-runs`), 상태(`GET .../event-runs/current`), 목록(`GET .../events`), 하나 조회(`GET .../events/{eventId}`)를 둔다(`docs/api-spec.md`). 기존 `text-changes` 응답은 바꾸지 않아 채팅의 `search_text_changes`에 영향이 없다.

**켜고 끄기:** backend 설정 `TEXT_EVENTS_ENABLED`(기본 false)로 끄고 켠다. 7.7의 켜는 기준을 통과할 때까지 끈다.

**가정(2.12 전에 정한 값):**

1. 후보 입력 약 3만 토큰이 호출 한 번에 들어가고 쓸 만한 시간에 답이 온다. 그래서 `/internal/text-events`는 다른 내부 호출과 별개의 제한시간을 쓴다. 값은 2.12에서 정한다.
2. 입력이 한도를 넘으면 후보를 나눠 묶고, 나온 사건의 제목과 변경 번호만으로 한 번 더 불러 합친다. 섹션으로 나누면 여러 섹션에 흩어진 사건이 쪼개지기 때문이다. 합치는 호출에는 원문이 없어 인용을 검증할 수 없으므로 묶기만 하고, 합친 사건은 앞 호출에서 검증한 인용과 근거 위치를 그대로 쓴다.
3. 모델에는 변경마다 글을 1,500자까지만 넣는다. 인용 검증은 저장된 전체 글이 아니라 모델에 넣은 글로 한다.
4. 후보 규칙은 2.14에서 삼성전자 핵심 사건 2건이 빠지지 않게 고친다. 고치지 못하면 7.7의 핵심 사건 기준을 통과할 수 없으므로 카드를 켜지 않는다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 분석 작업 안에서 요약처럼 만들기 | 실패가 분석 실패가 되어 AC21과 맞지 않습니다. 표가 먼저 보이지 않고, 자동 분석마다 비용이 들며, 프롬프트를 고칠 때마다 분석 버전을 올려 재분석이 필요합니다. |
| 분석 완료 직후 자동으로 백그라운드 실행 | 분석 실패와 분리되지만 열어 보지 않을 분석에도 비용이 듭니다. |
| 조회 요청 안에서 동기로 만들기(한 줄 풀이, 관련 수시공시 방식) | 호출이 수 분까지 걸릴 수 있어 요청이 끊기기 쉽고, 만드는 중과 실패를 나눠 보여 주기 어렵습니다. |
| ai-server에 실행 상태까지 두기 | ai-server는 DB가 없고, 상태·저장은 backend라는 구조 규칙과 맞지 않습니다. |
| 한 변경은 한 사건에만 묶기 | 규모 중복은 막지만 두 사건에 걸친 변경을 한쪽에서 잃어 근거가 빠집니다. 합계를 내지 않으면 중복 문제도 생기지 않습니다. |
| 기본 목록 전체를 나눠서 보내기(후보 규칙 없음) | 빠지는 사건은 없지만 약 15~17만 토큰으로 비용이 5배쯤이고, 쪼갠 뒤 합치는 단계에 더 기댑니다. 2.12에서 후보 규칙이 부족하다고 나오면 다시 봅니다. |

## 결과

- 좋아지는 점: 사건 실패가 분석과 표에 영향을 주지 않습니다. 열어 본 분석에만 비용이 들고, 프롬프트를 고쳐도 재분석이 필요 없습니다.
- 감수하는 점: 처음 여는 사람은 사건을 기다립니다. 비로그인 요청도 비용을 만들 수 있어 분석마다 성공 1번과 하루 실패 3번까지는 허용합니다. 버전을 올리면 열리는 분석마다 다시 호출합니다. 가정이 틀리면 입력 범위와 제한시간을 고쳐야 합니다. 로컬 fake에서는 사건이 만들어지지 않으므로 카드 흐름은 테스트의 고정 응답으로 확인합니다.
- 지켜야 할 것: 사건을 고쳐도 `Analysis.CURRENT_VERSION`은 올리지 않고 `TextEvents.EVENT_VERSION`을 올립니다. 저장 전에 `COMPLETED`로 바꾸지 않습니다. 사건마다 근거 위치, 모델, 프롬프트 버전, 호출 시각을 저장하고 'AI 생성' 표시를 코드로 붙입니다. 사건 규모를 합산해 보여 주지 않습니다. 7.7을 통과하기 전에 `TEXT_EVENTS_ENABLED`를 켜지 않습니다.

## 다시 볼 때

- 2.12에서 진짜 모델로 잰 입력 범위, 제한시간, 비용이 가정과 다를 때. 이 ADR을 채택한 뒤라면 새 ADR로 바꿉니다.
- 7.7에서 켜는 기준을 통과하지 못할 때.
- 3단계에서 신호·공시의 의미를 사건에 더할 때.
- 서버를 두 대 이상 띄워 시작 시 끊긴 실행 정리가 다른 서버의 실행까지 건드릴 때.
- 비로그인 호출 비용이 실제로 문제가 될 때.
