# ADR-0024: 기업 정보는 보고서에 딸린 자료는 접수번호로 한 번만, 바뀌는 자료는 받은 시각과 유효 시간으로 OpenDART에서 받아 저장한다

- 상태: 채택
- 결정한 날: 2026-10-26
- 관련: #329 (FS-45 기업 개황), #330·#331·#332·#333 (FS-46~49), [ADR-0003](0003-opendart-cache-in-backend-parsing-in-ai-server.md), [ADR-0005](0005-error-format-and-trace-id.md), [ADR-0017](0017-auto-increment-id-primary-key.md)

## 맥락

- 기업 화면에 '기업 개요' 탭(FS-45~49)을 두고 기업 개황, 재무 흐름, 주주·임원·배당, 최근 공시, AI 브리핑을 보여 준다. 모두 OpenDART에서 받는 기업 단위 자료다.
- OpenDART는 하루 호출 한도가 있고(넘으면 `020`), 개발용 키를 팀이 함께 쓴다(ADR-0003). 기업 화면을 열 때마다 여러 API를 부르면 한도에 금방 닿는다.
- 자료는 두 종류다.
  - 보고서에 딸린 자료: 주요 계정, 최대주주·임원·배당 현황처럼 사업·반기·분기보고서 하나(접수번호)에 묶여 있는 값. 보고서가 정정되면 접수번호가 새로 생기고, 같은 접수번호의 값은 바뀌지 않는다.
  - 바뀌는 자료: 기업개황(`company.json`: 대표자, 주소, 홈페이지 등)과 공시 목록(`list.json`)은 같은 요청이라도 시간이 지나면 값이 바뀐다.
- `company.json`은 고유번호(`corp_code`) 하나로 부르고, 없는 기업이면 `013`(조회된 데이타가 없습니다)을 돌려준다(2026-10-26 삼성전자 `00126380`과 없는 번호로 실제 호출해 확인).
- backend 규칙: 외부 호출은 트랜잭션 밖에서 하고 저장만 묶는다(conventions LY-2). 현재 시각은 주입한 `Clock`으로만 얻는다(EN-3).

## 결정

- **보고서에 딸린 자료**는 접수번호(`rcept_no`)를 키로 저장하고, 한 번 받으면(`013` 자료 없음 포함) 다시 받지 않는다. 정정 공시는 새 접수번호이므로 새로 받는다.
- **바뀌는 자료**는 받은 시각(`fetched_at`)과 함께 저장하고, 유효 시간이 지난 뒤에 요청이 오면 다시 받는다.
  - 기업개황: 7일(`app.company.overview-refresh-after`, `company_overview` 표)
  - 공시 목록(최근 공시, #332): 1시간
  - 기존 정기보고서 목록(ADR-0003, 24시간)은 그대로 둔다.
- **받는 순서**: 저장된 값이 유효하면 그대로 돌려준다. 아니면 트랜잭션 밖에서 OpenDART를 부르고, 받은 값만 트랜잭션으로 저장한다(같은 키를 동시에 처음 저장해 UNIQUE에 걸리면 한 번 더 저장해 있는 행을 고친다).
- **실패**: 다시 받다 실패하면(호출 실패·한도 초과·키 없음) 저장된 값이 있으면 그 값을 돌려주고 응답의 `refreshError`에 실패 코드를 담는다. 저장된 값이 없으면 정해진 에러(`DART_REQUEST_FAILED`·`DART_RATE_LIMITED`·`DART_KEY_MISSING`)로 끝낸다. 실패는 저장하지 않는다.
- **`013`**: 실패가 아니라 빈 결과다. '자료 없음'으로 저장하고(바뀌는 자료는 유효 시간 동안 다시 묻지 않음) 200으로 돌려준다.
- 공통 코드
  - 유효 판단: `com.dartinsight.dart.domain.CachePolicy`(`permanent()` 보고서에 딸린 자료, `refreshAfter(Duration)` 바뀌는 자료)
  - 받기·저장·실패 처리: `com.dartinsight.dart.service.DartCacheLoader`
  - 한 건짜리 JSON API 호출과 `status` 처리: `OpenDartClient.fetchJson`(`013`이면 빈 `Optional`)
  - 경로: `OpenDartPaths`
- 저장 표는 기본키를 자동 증가 `id`로 두고, 고유번호·접수번호는 UNIQUE로 둔다(ADR-0017).

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 요청마다 OpenDART를 부르기 | 기업 화면 한 번에 API 여러 개를 불러 한도에 금방 닿고, OpenDART가 느리거나 실패하면 화면이 같이 실패한다 |
| 모든 자료를 같은 유효 시간으로 다시 받기 | 접수번호에 묶인 값은 바뀌지 않아 다시 받을 이유가 없고 호출만 늘어난다 |
| 바뀌는 자료도 한 번 받으면 다시 받지 않기 | 대표자·주소가 바뀌어도 화면이 옛 값을 계속 보여 준다 |
| 서버 메모리 캐시(Caffeine 등) | 서버를 다시 띄우면 비고, 받은 시각을 화면에 보여 줄 수 없다. 이미 다른 OpenDART 자료를 DB에 두고 있다 |
| 백그라운드 작업으로 미리 받아 두기 | 전체 기업(약 10만)을 받으면 한도를 넘는다. 사용자가 연 기업만 받으면 충분하다 |

## 결과

- 좋아지는 점: 같은 기업 화면을 다시 열어도 OpenDART를 부르지 않는다. OpenDART가 실패해도 받아 둔 값을 받은 시각과 함께 보여 준다. FS-46~49가 같은 순서(`DartCacheLoader`)와 같은 실패 처리를 쓴다.
- 감수하는 점: 바뀌는 자료는 유효 시간 동안 옛 값일 수 있다(화면에 받은 시각을 보여 준다). 자료 종류마다 표가 하나씩 늘어난다.
- 지켜야 할 것: 새 OpenDART API를 쓸 때 보고서에 딸린 자료인지 바뀌는 자료인지 먼저 정하고, 바뀌는 자료면 유효 시간을 설정 값으로 둔다. OpenDART 호출은 트랜잭션 밖에서 한다. `013`은 에러로 바꾸지 않는다. 화면에 받은 시각(`fetchedAt`)과 출처를 함께 보여 준다.

## 다시 볼 때

- 호출 한도 초과(`020`)가 자주 나올 때(유효 시간을 늘리거나 미리 받기 검토)
- 서버를 여러 대로 늘려 같은 자료를 동시에 받는 일이 잦아질 때
- OpenDART가 변경 시각이나 조건부 요청을 제공할 때

## 구현 메모

- #358에서 FS-46~48을 공통 순서로 옮겼다(결정 내용은 그대로).
  - FS-46 재무 흐름(`FinancialTrendService`): `permanent()`. 받아 둔 기록은 보고서들을 한 번에 읽고, 없는 보고서만 `DartCacheLoader`로 받는다. 받지 못하면 그 기간만 `FETCH_FAILED`다.
  - FS-47 주주·임원·배당(`KeyFactService`): `permanent()`에 '자료 없음을 받은 뒤 보고서 목록에서 그 보고서를 다시 봤으면 한 번 더 받기'를 `usable` 조건으로 둔다. 받지 못하면(저장된 자료 없음을 다시 받다 실패한 경우 포함) 그 묶음만 `UNAVAILABLE`이다.
  - FS-48 최근 공시(`DisclosureService`): `refreshAfter(1시간)`에 '받은 기간이 요청 기간을 덮는지'(`DisclosureFetch.covers`)를 `usable` 조건으로 둔다.
- `DartCacheLoader.load`는 유효 시간 말고 저장된 값을 그대로 쓸 조건(`usable`)을 받는 형태가 하나 더 있다. 조건에 맞지 않아 다시 받다 실패해도 저장된 값과 실패 코드를 돌려준다.
- 주요계정(`fnlttSinglAcnt.json`)과 정기보고서 주요정보(`hyslrSttus`·`exctvSttus`·`alotMatter`)도 `fetchJson`으로 부른다. 제네릭 응답 record는 `ParameterizedTypeReference`를 받는 `fetchJson`을 쓴다.
