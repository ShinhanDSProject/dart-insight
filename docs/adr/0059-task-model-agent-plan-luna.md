# ADR-0059: LLM 모델을 작업마다 덮어쓸 수 있게 하고, 에이전트의 Tool 고르기(agent_plan)는 gpt-6-luna로 부른다

- 상태: 채택
- 결정한 날: 2026-11-06
- 관련: #742(3.44), #633(3.35, 측정), PR #732(캐시·추론 토큰 기록), [ADR-0026](0026-openai-llm-provider.md)(기본 모델, 그대로 둠), [ADR-0008](0008-single-llm-module.md), [ADR-0049](0049-agent-plan-writes-answer.md)(고르기가 답 초안도 씀), 노션 결정 로그 초안 '에이전트 Tool 고르기 속도·비용 개선 방향(#633)'

## 맥락

- 에이전트 채팅 한 번에 평균 약 1.9만 토큰, 약 0.026달러가 듭니다(2026-11-06 실측 5건, 캐시 반영). 그중 Tool 고르기(`agent_plan`) 한 번의 입력이 약 1만 토큰이고, 채팅마다 한 번 이상 부릅니다.
- 지금은 모든 작업이 같은 모델을 씁니다. `LLM_MODEL` 하나이고 기본은 `gpt-6.1-sol`입니다(ADR-0026, `app/core/config.py`의 `LlmSettings.model`).
- 가격(100만 토큰당 입력/캐시 입력/출력, 모델 페이지 2026-11-06): `gpt-6.1-sol` 2/0.1/10달러, `gpt-6-luna` 0.1/0.01/0.5달러. 둘 다 구조화 출력과 추론을 지원합니다. 이 키로 쓸 수 있는 모델은 OpenAI 모델 목록 API로 확인했습니다.
- #633 측정(첫 단계 고르기, 질문 10개): luna는 9/10 맞게 골랐습니다(sol 10/10). 틀린 1건은 '부채비율'을 체크포인트가 아니라 재무 계정에서 찾은 것입니다. 평균 시간은 2.86초로 sol 3.64초와 비슷하고, 호출당 비용은 캐시 없이 약 0.0011달러로 sol 약 0.021달러의 약 1/20입니다.
- 고르기 호출은 자료가 충분하면 답 초안도 씁니다(ADR-0049). 그래서 #742에서 Tool 결과를 받은 2단계 10개를 서비스 그래프 그대로 돌려 답 품질을 쟀습니다.

  | 경우 | 답함 | 찾지 못함 | Tool을 더 부름 | 반려 | 평균 | 단계당 비용 |
  | --- | --- | --- | --- | --- | --- | --- |
  | 고르기 sol, 답 sol(지금) | 6 | 1 | 3 | 1 | 6.2초 | 0.0168달러 |
  | 고르기 luna, 답 sol | 6 | 0 | 4 | 0 | 6.4초 | 0.0009달러 |
  | 모두 luna | 5 | 1 | 4 | 2 | 5.7초 | 0.0004달러 |

  고르기 luna에서는 답 6개를 모두 luna가 초안으로 썼고, 검토 노드(근거·숫자·원인 표현·등급·표현 검사)를 반려 없이 통과했습니다. 모두 luna로 하면 '숫자가 Tool 결과에 없음' 반려가 2번 나왔습니다.

## 결정

- `LlmSettings`에 작업별 모델 `task_models`(task 이름 → 모델 ID)를 둡니다. `LlmClient`가 요청의 `task`로 모델을 고르고, 없으면 지금처럼 `LlmSettings.model`(기본 `gpt-6.1-sol`)을 씁니다. 제공자 호출에 모델을 넘기는 곳은 `app/llm/` 안뿐입니다(ADR-0008).
- 환경 변수 `LLM_TASK_MODELS`로 정합니다. 형식은 `task=모델`을 쉼표로 이은 글자입니다(예: `agent_plan=gpt-6-luna`). 변수가 없으면 코드의 기본값 `agent_plan=gpt-6-luna`를 쓰고, 빈 값이면 작업별 모델을 쓰지 않습니다. 제공자가 `fake`이면 쓰지 않습니다.
- 에이전트의 Tool 고르기(`agent_plan`, 답 초안 포함)는 `gpt-6-luna`로 부릅니다. 답 쓰기(`agent_answer`, 초안이 없거나 반려된 뒤 다시 쓰기)는 기본 모델 그대로입니다. 다른 작업(요약·풀이·브리핑·전망·계획 대조·주요 사건·근거 질문)은 바꾸지 않습니다.
- 호출 기록(`llm_call.model`, 응답 `ai.model`)에는 실제로 부른 모델이 남습니다. 답 초안을 고르기가 썼으면 공개 응답의 `ai.model`도 `gpt-6-luna`입니다.
- 프롬프트·검토 규칙은 바꾸지 않으므로 `PROMPT_VERSION`은 올리지 않습니다. 모델은 호출 기록으로 구분합니다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 지금처럼 모든 작업을 `gpt-6.1-sol`로 | 고르기 단계 비용이 약 18배입니다. 측정에서 luna 초안이 검토를 모두 통과해 품질 이득이 보이지 않았습니다. |
| 에이전트 전체(고르기·답 쓰기)를 `gpt-6-luna`로 | 단계당 비용은 더 낮지만, 답 쓰기에서 숫자 반려가 2번 나왔습니다. 반려 뒤 다시 쓰기는 기본 모델이 맡는 편이 안전합니다. |
| `LLM_MODEL` 자체를 `gpt-6-luna`로 | 요약·풀이처럼 실측하지 않은 작업의 품질까지 함께 바뀝니다. |
| `gpt-6.1-terra`(입력 1달러, 출력 5달러) | 고르기 정확도 9/10에 평균 4.07초로 sol보다 느렸고, 비용은 luna의 약 10배입니다. |
| 고르기에서 답 초안을 빼고 답은 늘 sol이 쓰기 | 호출이 한 번 늘어 ADR-0049로 줄인 시간(채팅 평균 15.2초 → 10.2초)을 되돌립니다. |

## 결과

- 좋아지는 점: 채팅 비용의 큰 몫인 고르기 단계가 약 1/18로 줍니다. 작업마다 모델을 따로 실험·적용할 수 있습니다.
- 감수하는 점: 측정은 질문 10개(분석 14) 기준입니다. luna가 Tool을 덜 정확히 고르거나(예: 부채비율), 자료를 더 찾기로 해 왕복이 느는 경우가 있을 수 있습니다. 시간 이득은 없습니다.
- 지켜야 할 것
  - 작업별 모델을 바꾸면 이 ADR이나 새 ADR에 근거(측정)를 남깁니다.
  - 모델 ID는 짐작하지 않고 제공자의 모델 목록·가격 페이지로 확인합니다.
  - 배포 환경에서 `LLM_TASK_MODELS`를 따로 정하면 그 값이 코드 기본값보다 앞섭니다.

## 다시 볼 때

- 호출 기록에서 `agent_plan` 고르기의 반려나 '찾지 못함' 비율이 sol 때보다 눈에 띄게 늘 때
- 모델 가격·목록이 바뀌거나 `gpt-6-luna`가 지원 중단될 때
- 다른 작업(요약·풀이 등)도 작은 모델로 바꾸려 할 때(그 작업을 실측한 뒤)
