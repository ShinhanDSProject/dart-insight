# ADR-0060: 사건 신호는 AI가 묶을 때 고른 종류·변화로 ai-server 코드가 기준표에서 붙이고, 공시의 의미와 신호 이유는 묶기 뒤 사건마다 따로 부른다

- 상태: 채택
- 결정한 날: 2026-11-06
- 관련: 이슈 #731(2.20), 기획서 초안 '문장 변화 탭 개편' 3단계(R7~R11, R14, R17, R18, AC12~AC20, AC24, AC28, AC29. FS 번호는 등록 후 채움), #729(5.7, `AGENTS.md` 신호 예외), #730(7.8, `ai-server/app/events/signal_table.json`), [ADR-0050](0050-text-events-after-analysis.md), [ADR-0051](0051-text-event-candidate-rules.md), [ADR-0053](0053-event-scale-amount-candidates.md)(맨 앞 종류 판정을 대체), [ADR-0057](0057-text-event-llm-limits.md)(backend 대기 시간을 대체), [ADR-0058](0058-event-amount-confirmation.md), [ADR-0059](0059-task-model-agent-plan-luna.md)

## 맥락

- 5.7에서 `AGENTS.md`가 바뀌어 주요 사건에 긍정·주의·보류 신호를 붙일 수 있다. 신호는 LLM이 정하지 않고, LLM이 근거 ID와 함께 고른 사건 종류·변화로 코드 기준표가 붙인다. 근거를 확인하지 못했거나 기준표에 없으면 보류이고, 규모는 신호를 바꾸지 않는다.
- 7.8에서 기준표 `signal_table.json`(`signal-table-1`)을 ai-server에 두었다. 종류 30개, 종류마다 변화와 신호(`CAUTION`, `POSITIVE`, `MIXED`, `null`), `explicitOnly`, 보여 줄 계정, 보류(`MIXED`)의 일반 문구(`generalSides`), 용어 풀이 10개가 있다. 용어 풀이는 모두 출처를 확인하지 못했다. 주의·긍정 변화의 일반 문구는 없다.
- 지금 사건은 묶기 호출(`text-event-2`) 한 번으로 만들고, `kind`는 AI가 쓴 자유 글이다. 맨 앞 종류는 ADR-0053대로 제목·종류의 낱말로 판정한다(`app/events/ordering.py`).
- 묶기 호출은 이미 무겁다. 7.7 1차에서 세 기업의 사건은 25/26/23건, 전체 시간은 111.4/108.1/62.0초이고, ADR-0057은 묶기 호출당 240초, 전체 480초, 출력 32,000, 금액 예산 240초, backend 대기 900초로 정했다.
- 기획서는 카드마다 AI 문장 두 칸을 둔다. 공시의 의미(무엇이 바뀌었고 무슨 뜻인가, '없음' 문장은 확인한 범위를 적음)와 신호 이유(판정 줄 아래 근거 2~3개, 보류면 좋은 면·나쁜 면, 섞인 소송은 판단하지 않은 이유)다. 실패하면 각각 다르게 끝난다(AC16 용어 풀이만, AC20 일반 문구와 '일반적인 설명이에요.').
- `LlmClient.generate`는 호출마다 상태를 지역 변수로 두고, 작업(`task`)마다 모델을 덮어쓸 수 있다(ADR-0059).
- 가격은 `gpt-6.1-sol` 100만 토큰당 입력 2달러, 출력 10달러다(ADR-0059, 모델 페이지 2026-11-06).

## 결정

### 신호

**종류·변화는 묶기 호출에서 고른다.** 묶기 프롬프트를 `text-event-3`으로 올리고, 사건마다 기준표의 종류 코드(`signalKind`), 그 종류의 변화 코드(`signalChange`), 근거 ID(`signalEvidenceId`)를 받는다. 기준표의 종류·변화 목록(코드와 이름)을 프롬프트에 넣는다. AI는 신호 값을 쓰지 않는다. 사건을 정하는 호출에서 종류도 정해야 묶음과 종류가 어긋나지 않고, 출력이 사건마다 세 값만 늘어난다.

**신호는 ai-server 코드가 붙인다**(새 모듈 `app/events/signals.py`, 기준표를 읽는 곳은 이 모듈 하나). 순서대로 본다.

1. 종류·변화가 기준표에 없으면 보류, 사유 `NO_CRITERIA`. `kind`는 기준표의 '그 밖의 사건'이다.
2. `signalEvidenceId`가 그 사건의 검증된 인용(`quotes`) 중 하나의 근거 ID가 아니면 보류, 사유 `EVIDENCE_NOT_CONFIRMED`. `explicitOnly` 변화는 그 인용이 이번 보고서 쪽(`side: CURRENT`)이어야 한다. 이전 글이 삭제된 것만으로는 해소로 보지 않는다.
3. 종류가 소송이고 묶인 표 변경의 행 비교에서 바뀐·새·이번엔 없는 행이 합쳐 2행 이상이면, AI가 고른 변화와 상관없이 보류, 사유 `MIXED_LITIGATION`(AC19). 행 수는 backend가 보내는 `rowCounts`를 코드가 더한다.
4. 기준표의 신호가 `null`이면 보류, 사유 `NO_CRITERIA`. `MIXED`면 보류, 사유 `MIXED_SIDES`. `CAUTION`·`POSITIVE`는 그대로다.

밖으로 내보내는 신호는 `CAUTION`, `POSITIVE`, `HOLD` 셋이고, 보류면 `holdReason`이 있다. 규모(금액·비율)는 이 판정에 들어가지 않는다.

**맨 앞 종류는 기준표로 판정한다.** 기준표에서 `front: true`인 종류의 `OCCURRED`이고 위 2번까지 통과했을 때만 `sortBasis: FRONT_KIND`다. ADR-0053의 낱말 판정(제목·종류의 낱말, 이번 글에만 있음)을 대체한다. 순서의 나머지(금액, 바뀐 단위 수, 문서 순서)는 ADR-0053 그대로다.

**기준표 버전:** 실행마다 `signal_table_version`을 저장한다. 기준표의 결과가 달라지게 바꾸면(종류·변화·신호·`explicitOnly`·계정·일반 문구·용어) 표의 `version`과 `TextEvents.EVENT_VERSION`을 함께 올린다. 화면의 '기준 보기'는 지금 기준표를 보여 주고, 조회는 현재 사건 버전만 하므로 사건과 표의 버전이 어긋나지 않는다. backend는 ai-server의 `GET /internal/signal-tables/current`를 받아 버전별로 메모리에 두고 `GET /api/signal-tables/current`로 내보낸다. 기준표 파일은 ai-server에만 둔다.

### 사건 문장

**묶기와 금액 확인이 끝난 뒤, 같은 내부 요청(`POST /internal/text-events`) 안에서 사건마다 두 번 따로 부른다.** task는 `event_meaning`(프롬프트 `event-meaning-1`, 새 모듈 `app/events/meaning*.py`)과 `event_signal_reason`(프롬프트 `event-signal-reason-1`, `app/events/signal_reason*.py`)이다. 신호 이유는 신호와 행 수가 정해진 뒤에야 쓸 수 있고, 두 칸은 검증·재생성·실패 표시가 달라 따로 다시 만든다.

- 입력: 그 사건의 인용, 묶인 변경 글(ADR-0051의 1,500자 제한), 코드가 정한 값(종류·변화 이름, 신호, 보류 사유, 금액·비율, 행 수, `MIXED`면 기준표의 일반 문구). 원문은 구분 태그로 감싼다. 건수·금액·비율은 코드 값만 쓴다.
- 신호 이유는 신호가 `CAUTION`·`POSITIVE`이거나 보류 사유가 `MIXED_SIDES`·`MIXED_LITIGATION`일 때만 만든다. `NO_CRITERIA`·`EVIDENCE_NOT_CONFIRMED`는 정해진 문구만 보이고 부르지 않는다.
- 문장마다 근거 ID가 있고, 그 사건에 묶인 변경의 블록(`{rcept_no}#B{block_no}`)이어야 한다. 금액·날짜·사건번호·회사 이름의 원문 대조와 '없음' 문장의 확인 범위 검사는 2.22에서, 표현 검사(`expr-1`)는 두 칸 모두 거친다.
- 검증에 실패하면 `LlmClient`의 재생성(최대 2회)을 쓰고, 그래도 실패하면 공시의 의미는 `FAILED`(문장 없음, 용어 풀이만 보임), 신호 이유는 `FALLBACK`(기준표의 일반 문구, AI 생성 아님, '일반적인 설명이에요.')이다. `MIXED_LITIGATION`의 `FALLBACK`은 문구 없이 판정 줄과 행 수만 보인다. 문장 하나가 실패해도 실행은 실패하지 않는다.
- 주의·긍정 변화의 일반 문구가 기준표에 없으므로 2.23에서 더하고 `signal-table-2`로 올린다.

**제한:** 문장 단계는 별도 예산 300초 안에서 최대 4개를 동시에 부른다(`app/events/sentences.py`의 상수). 호출당 제한시간 60초, 요청 전체 120초(`LlmSettings` 기본값과 같음), 출력 한도 4,000이다. 예산을 넘기거나 LLM을 쓸 수 없으면 남은 칸은 공시의 의미 `FAILED`, 신호 이유 `FALLBACK`이고 사유는 각각 `BUDGET_EXCEEDED`·`LLM_UNAVAILABLE`이다. backend `text-events-read-timeout`은 900초에서 1,200초로 올린다(최악 480 + 240 + 300에 예산 끝에 시작한 호출의 120초를 더한 1,140초보다 길게). ADR-0057의 backend 900초를 대체하고 나머지 값은 그대로 둔다. 동시 호출이 제공자 한도에 걸리면 7.9에서 줄인다.

**용어 풀이:** AI를 부르지 않는다. 기준표 용어 중 출처를 확인한 것(`source`가 있음)이고 그 사건의 인용 글에 그 낱말이 있으면 코드가 붙인다. 지금은 출처를 확인한 용어가 없어 항상 빈 목록이다.

**사실 칸:** ai-server는 기준표의 계정 이름만 사건에 붙인다(`factAccounts`, `accountsByType`이 있으면 유형 이름과 함께). 값은 backend가 조회할 때 같은 분석의 `financial_change`에서 재무상태표(`BS`)의 계정명(공백을 뺀 것)이 같은 행을 찾아 재무 수치 탭과 같은 값을 그대로 쓴다. 찾지 못하면 칸이 없다. 계정 코드는 추측하지 않는다.

### 저장과 버전

- backend는 신호와 문장을 사건과 같은 트랜잭션에서 저장한 뒤 `COMPLETED`로 바꾼다(ADR-0050). 문장은 새 테이블 `text_event_sentence`에 칸마다 한 행으로 두고, 문장별 근거 ID, 상태, 실패 사유, 모델, 프롬프트 버전, 호출 시각을 저장한다(`docs/erd.md`).
- backend는 저장하기 전에 `signalEvidenceId`가 그 사건 인용의 근거 ID인지, 문장의 근거 ID가 묶인 변경의 블록인지 다시 확인한다. 신호 근거가 어긋나면 인용이 어긋날 때와 같이 실행을 `FAILED`로 끝낸다. ai-server가 이미 확인한 값이라 어긋나면 결함이고, 그 신호로 정한 순서와 신호 이유를 backend가 고칠 수 없기 때문이다. 문장 근거가 어긋나면 그 칸만 실패(신호 이유는 대체 표시)로 저장하고 실행은 실패시키지 않는다.
- `TextEvents.EVENT_VERSION`을 `event-4`로 올린다. ADR-0050대로 조회는 현재 버전만 하므로 `event-3` 사건은 보이지 않고, 분석을 다시 열면 새로 만든다. 옛 행은 지우지 않고 새 칸은 null로 둔다. 재분석은 필요 없다.

### 구현 이슈

신호와 맨 앞 종류는 #733(2.21), 공시의 의미와 용어 풀이, 문장 단계의 제한은 #734(2.22), 신호 이유와 일반 문구는 #735(2.23), 저장·조회 API·기준표 조회·신호 거르기·사실 칸 값·`EVENT_VERSION`·backend 대기 시간은 #736(3.40)에서 한다.

### 비용과 시간 어림 (모델을 부르지 않은 어림, 7.9에서 잰다)

- 호출 수: 기업당 사건 23~26건(7.7 1차) × 두 칸. 신호 이유를 만들지 않는 보류를 빼면 기업당 약 40~50번이다. 지금은 묶기 1번과 금액 확인 약 11번이다.
- 입력: 호출당 프롬프트 약 1,500토큰 + 묶인 변경 글(사건당 변경 3~5개, 글 1,500자 제한)로 약 3,000~6,000토큰. 출력: 문장과 추론을 합쳐 약 1,000~2,000토큰.
- 비용: 기업당 약 0.5~1.5달러가 늘어난다. 7.7 1차의 묶기와 금액 확인은 세 기업 합계 약 0.78달러(기업당 약 0.26달러)였으므로 약 3~6배다. 재생성이 일어나면 그 칸은 최대 3배다.
- 시간: 호출당 5~15초로 보면 4개 동시에 약 1~3분이 늘어 묶기와 합쳐 기업당 약 3~5분이다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 공시의 의미와 신호 이유를 묶기 호출에서 함께 쓰기 | 출력이 사건마다 문장 두 칸만큼 늘어 32,000·240초 한도(ADR-0057)를 넘기 쉽습니다. 문장 하나가 검증에 실패하면 묶기 전체를 다시 만들고, 신호와 행 수가 정해지기 전이라 신호 이유를 쓸 수 없습니다. |
| 사건 하나에 한 번 불러 두 칸을 함께 쓰기 | 입력이 겹치지 않아 입력 비용이 절반 가까이 줄지만, 한 칸만 실패해도 두 칸을 함께 다시 만들고, 두 칸의 실패 표시(AC16, AC20)를 나눠 다루기 어렵습니다. 비용이 문제면 7.9 뒤에 다시 봅니다. |
| 모든 사건의 문장을 한 번에 쓰기 | 호출은 적지만 사건 하나의 실패가 전체 재생성이 되고, 출력이 묶기만큼 커집니다. |
| 사건을 펼칠 때 문장을 만들기 | 공시의 의미와 신호 이유는 펼치기 전 카드에 보입니다(시안). 조회마다 LLM을 부르게 되어 비동기 작업 규칙과도 맞지 않습니다. |
| 문장을 별도 내부 요청·실행으로 나누기 | 문장만 다시 만들 수 있지만, 실행 상태와 재시도 규칙(ADR-0050)이 하나 더 생기고 backend가 두 번 저장합니다. 지금 이슈 범위(3.40)는 한 요청을 저장하는 것입니다. |
| 신호를 backend가 붙이기 | 기준표가 ai-server에 있고, 묶기 검증·맨 앞 종류·신호 이유 입력이 모두 ai-server에서 신호를 씁니다. 두 서비스에 표를 두면 버전이 어긋날 수 있습니다. |
| 기준표를 backend나 frontend에 복사하기 | 같은 이유로 버전이 어긋날 수 있습니다. 조회 API 하나로 같은 파일을 보여 줍니다. |

## 결과

- 좋아지는 점: 같은 종류·변화는 늘 같은 신호입니다(AC12). AI가 신호나 숫자를 쓰지 않습니다. 문장 하나가 실패해도 사건과 신호는 남습니다. 기준표를 파일 하나와 버전 하나로 관리합니다.
- 감수하는 점: 사건 만들기 비용이 약 3~6배, 시간이 기업당 1~3분 늘고, 최악에는 backend 스레드를 20분까지 잡습니다. AI가 종류나 변화를 잘못 고르면 신호도 틀립니다(7.9에서 일치율을 잽니다). 소송 섞임은 행 수만 보므로 같은 소송의 여러 행이 바뀌어도 섞인 것으로 봅니다. 사실 칸은 이름이 같은 재무상태표 계정만 찾아 많은 사건에서 칸이 없을 수 있습니다. 용어 풀이는 출처를 확인하기 전까지 비어 있습니다. 버전을 올리면 열리는 분석마다 다시 부릅니다.
- 지켜야 할 것: 신호는 `signals.py`의 기준표 판정으로만 붙입니다. 기준표, 묶기·문장 프롬프트, 검증을 바꾸면 해당 버전과 `EVENT_VERSION`을 올립니다. 신호를 보여 주는 화면에는 `signalNotice`를 둡니다. ai-server 쪽 시간을 올리면 backend `text-events-read-timeout`이 합보다 긴지 봅니다.

## 다시 볼 때

- 7.9에서 비용·시간이 어림과 크게 다르거나, 종류·변화 일치율이 낮을 때. 문장 작업을 작은 모델(ADR-0059의 작업별 모델)로 부를지도 이때 봅니다.
- 소송 섞임을 행 수로 판정해 잘못 보류되는 사건이 많을 때.
- 용어 풀이의 출처를 확인했을 때, 또는 사실 칸에서 재무상태표 밖의 계정이 필요할 때.
- 문장만 다시 만들어야 할 일이 잦을 때.
