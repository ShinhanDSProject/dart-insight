# ADR-0037: 이번 시즌 변화가 큰 기업은 대표 기업을 문장 비교만으로 재어 순위를 정하고, Top 10만 요약까지 분석한다

- 상태: 채택
- 결정한 날: 2026-10-27
- 관련: [#420](https://github.com/ShinhanDSProject/dart-insight/issues/420)(1.7), 선행 #399(대표 기업)·#16(문장 변경)·#29(결과 저장), [ADR-0033](0033-featured-companies-from-public-data-portal.md), [ADR-0004](0004-async-analysis-job.md)

## 맥락

- 첫 화면에 "이번 시즌 정기보고서의 문장이 전년 동기보다 많이 바뀐 대표 기업 Top 10"을 보여 준다(2026-10-27 화면 시안). 대상은 대표 기업 100곳(`featured_company`)이다.
- Top 10을 고르려면 후보 100곳을 모두 비교해 봐야 한다. 분석 하나(`AnalysisService.request`)는 원문·재무를 받고 문장 비교와 LLM 요약을 하므로, 100곳을 모두 분석하면 시즌마다 요약 100건의 비용이 든다.
- 문장 비교(`TextComparisonService.compare`)는 원문 받기·구조화·ai-server 비교만 하고 LLM을 부르지 않는다. 문장 변경마다 ai-server가 확인 우선순위 점수(섹션 가중치 포함, `ai-server/app/compare/priority.py`, 2.6)를 붙인다.
- 정기보고서는 1년에 4번이다. 제출 기한은 분기·반기보고서가 기간 끝 뒤 45일, 사업보고서가 90일이다(자본시장법 제159조·제160조, 노션 공시·재무 도메인 가이드로 다시 확인).
- 서버는 한 대다. OpenDART 공용 키에는 하루 호출 한도가 있다.

## 결정

- 시즌은 정기보고서 종류와 사업연도다(예: 2026 반기). 그 시즌의 보고서를 같은 종류의 전년 보고서와 비교한다(`YOY`).
- 시즌마다 한 번, 대표 기업 100곳마다 두 보고서를 정기보고서 목록(4.1)에서 고르고 `TextComparisonService.compare`만 부른다. 분석(`analysis`)은 만들지 않아 분석 목록과 섞이지 않고 LLM 비용이 없다. 결과는 기업마다 `season_change` 한 줄(점수·건수·한 줄 요약 또는 빠진 사유)로 저장하고 문장 변경 행은 저장하지 않는다(`season.service.SeasonChangeRanker`).
- 점수(`season-1`): 추가·삭제·수정(`ADDED`·`DELETED`·`MODIFIED`) 변경의 확인 우선순위 점수 합 ÷ (두 원문 블록 수 평균 ÷ 1,000). 숫자만 바뀜·위치 이동·검토 필요는 넣지 않는다. 문서가 길수록 변경이 많아지는 것을 1,000블록당으로 맞춘다. 순위는 점수가 높은 순, 같으면 고유번호 순이다.
- 한 줄 요약은 코드가 만든다: 최상위 섹션과 변경 종류별 점수 합이 큰 두 묶음을 '사업의 내용 수정 31곳 · 위험관리 문단 12개 추가'처럼 잇는다.
- 점수 상위 10곳만 `AnalysisService.request(..., YOY)`로 요약까지 있는 분석을 요청하고 `analysis_id`를 남긴다(같은 쌍이 있으면 다시 쓴다). 시즌당 LLM 요약은 10건이다. 요청에 실패했거나(호출 한도 등) 분석이 완료되지 않은 줄(실패, 서버가 멈춰 대기·진행 중으로 남음)은 하루마다 확인할 때 가장 최근 시즌에서 다시 요청한다(`retryAnalyses`). 요청은 같은 쌍을 다시 쓰므로 정말 진행 중이면 같은 분석이 돌아온다.
- 그 시즌 보고서나 전년 보고서가 없거나(`NO_REPORT`), 문장 비교가 실패·일부만 됐으면(`FAILED`) 순위에서 빼고 사유와 함께 저장한다. 화면은 빠진 수를 보인다.
- 언제: 서버 시작 2분 뒤(`app.season-changes.first-check-delay`, 대표 기업 목록을 먼저 받게)와 그 뒤 하루마다(`check-interval`) 확인해, 제출 기한 뒤 7일(`grace-days`)이 지났는데 아직 계산하지 않은 가장 최근 시즌을 계산한다(`Season.latestDue`). 계산한 시즌은 다시 계산하지 않는다(정정 보고서·늦은 제출은 반영하지 않음). 끄려면 `SEASON_CHANGES_ENABLED=false`.
- API는 `docs/api-spec.md` `GET /api/season-changes`, 표는 `docs/erd.md` `season_change`에 있다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 100곳 모두 요약까지 분석 | 순위에 요약은 필요 없는데 시즌마다 LLM 요약 100건이 든다 |
| 분석에 '요약 없음' 옵션을 붙여 100곳을 분석 | 요약 없는 분석 100개가 이미 분석한 비교 목록·재사용 규칙에 섞이고, 같은 쌍을 사용자가 요청하면 요약 없는 결과를 다시 쓰게 된다 |
| 후보를 시가총액 상위 30곳으로 줄인다 | 비용은 줄지만 문장 비교에는 LLM 비용이 없어 줄일 이유가 작고, 순위가 큰 회사 안으로 좁아진다 |
| 새 가중치 표를 만든다 | 문장 변경 화면의 확인 우선순위와 기준이 둘로 나뉜다. 같은 점수를 더해 쓴다 |
| 공시 건수·주가 변동으로 순위 | 정기보고서의 '바뀐 내용'과 상관이 없고, 주가는 투자 판단과 엮인다 |

## 결과

- 좋아지는 점: 시즌당 AI 비용은 요약 10건이고, 첫 화면은 저장된 순위만 읽는다. 점수 기준이 문장 변경 화면의 우선순위와 같다.
- 감수하는 점: 시즌마다 OpenDART 원문 최대 200건과 ai-server 비교 100번을 차례로 해 몇십 분 걸린다. 그동안 같은 스케줄 스레드를 쓰는 다른 주기 작업(즐겨찾기 폴링 등)이 뒤로 밀린다. 기한 뒤 7일이 지나 계산하므로 그 뒤 늦게 낸 보고서·정정은 그 시즌 순위에 없다. 문서 길이 보정은 단순 비례라 아주 짧은 문서는 점수가 커질 수 있다(대상이 대표 기업이라 크지 않음).
- 지켜야 할 것: 점수·순위는 코드가 계산하고 LLM에 맡기지 않는다. 점수 식을 바꾸면 `score_version`을 올린다. 화면은 순위를 좋고 나쁨으로 표현하지 않는다.

## 다시 볼 때

- 늦은 제출·정정을 순위에 넣어야 할 때(다시 계산 규칙)
- 대표 기업 수가 크게 늘거나, 서버를 두 대 이상 띄울 때
- 우선순위 규칙(`priority.py`)이 바뀌어 점수가 크게 달라질 때
