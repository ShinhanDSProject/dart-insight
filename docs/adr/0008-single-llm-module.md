# ADR-0008: LLM은 ai-server의 LlmClient 하나로만 부르고, 제공자를 정하기 전에는 가짜 제공자를 쓴다

- 상태: 채택(호출 기록을 분석이 완료될 때만 저장하는 부분은 ADR-0042가 대체)
- 결정한 날: 2026-10-22
- 관련: [이슈 #50](https://github.com/ShinhanDSProject/dart-insight/issues/50)(0.7), [PR #100](https://github.com/ShinhanDSProject/dart-insight/pull/100), 노션 결정 로그 [LLM 제공자·모델 선택](https://app.notion.com/p/400b6afffc6f8192bbd7e98fb597c38b)(미결정), 노션 개발 기준 3·8장

## 맥락

- LLM 제공자·모델과 키를 누구 이름으로 발급할지 아직 정하지 않았습니다. 그래도 요약(3.2) 같은 기능은 M2까지 만들어야 합니다.
- 모델 교체, 호출 기록, 비용 집계, 나중의 Kill Switch를 한곳에서 하기로 했습니다.
- LLM은 숫자를 지어내거나 형식이 틀린 답을 낼 수 있습니다. 검증에 실패하면 최대 2회까지만 다시 생성하고, 그래도 실패하면 '검토 필요'로 끝내야 합니다(개발 기준 8장).
- CI와 팀원 PC에는 LLM 키가 없습니다.

## 결정

- ai-server의 LLM 호출은 모두 `app/llm/client.py`의 `LlmClient.generate(request, validate)`를 거칩니다. 다른 모듈은 제공자 SDK를 직접 가져오지 않습니다.
- 제공자 연결은 `app/llm/providers.py`에만 둡니다. 지금은 가짜 제공자(`LLM_PROVIDER=fake`)만 있고, 작업별 응답기(`FAKE_RESPONDERS`)가 정해진 답을 돌려줍니다. `LLM_PROVIDER`를 비우면 LLM을 부를 수 없고(`LlmUnavailable`), 요약이 필요한 분석은 실패(`ANALYSIS_SUMMARY_FAILED`)로 끝납니다.
- 결과는 JSON으로 받고, 부른 쪽이 넘긴 `validate`가 검사합니다. 문제가 있으면(`OutputProblem`) 문제를 알려 주며 다시 생성합니다. 다시 생성은 최대 2회이고 설정으로도 2회를 넘길 수 없습니다. 끝내 실패하면 `LlmOutputInvalid`로 마지막 결과를 함께 넘겨, 부른 쪽이 통과한 부분만 쓰게 합니다.
- 네트워크 오류 같은 일시 오류는 `LLM_MAX_RETRIES`(기본 2)번까지 다시 시도하고, 요청 하나에 쓰는 전체 시간은 `LLM_TOTAL_TIMEOUT_SECONDS`(기본 120초)까지입니다.
- 호출마다 `CallRecord`(작업, 제공자, 모델, 프롬프트 버전, 호출 시각, 추적 ID, 토큰 수, 걸린 시간, 시도 번호, 결과)를 남기고, 분석이 완료되면 backend가 결과와 함께 `llm_call` 표에 저장합니다. 지금은 LLM을 부를 수 없어(`LlmUnavailable`) 분석이 실패하면 그때까지의 호출 기록이 저장되지 않습니다.
- 공시 원문은 `app.llm.prompting.disclosure`로 구분 태그에 감싸 지시가 아닌 자료로 넣습니다. 사용자 정보는 프롬프트에 넣지 않습니다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 기능마다 제공자 SDK를 직접 부르기 | 재시도·재생성 상한·호출 기록·비용 집계가 흩어지고, 제공자를 바꿀 때 여러 곳을 고쳐야 합니다. |
| LangChain의 모델·체인을 기능에서 바로 쓰기 | 제공자를 정하지 않은 지금은 얻는 것이 적고, 재생성 상한과 호출 기록 형식은 어차피 우리가 정해야 합니다. 제공자를 정하면 LangChain 모델을 `providers.py`의 제공자 하나로 연결할 수 있습니다. |
| 제공자를 정할 때까지 요약 기능을 미루기 | M2 일정을 맞출 수 없고, 근거·숫자 검증과 '검토 필요' 흐름을 미리 시험할 수 없습니다. |

## 결과

- 좋아지는 점: 키 없이 CI와 로컬에서 분석 전체 흐름을 돌립니다. 제공자를 정하면 `providers.py`와 설정만 바꿉니다. 완료된 분석마다 호출 기록이 남습니다.
- 감수하는 점: 가짜 제공자의 답으로는 요약 품질을 평가할 수 없습니다. 실제 제공자를 연결한 뒤 실제 원문으로 다시 평가해야 합니다(7.3). 실패한 분석의 호출 기록이 남지 않아, 실제 제공자를 쓰면 비용 집계에 빈틈이 생깁니다.
- 지켜야 할 것: LLM을 부르는 새 기능도 `LlmClient`와 `validate`를 거치고, 프롬프트 버전을 올리면 분석 버전도 올립니다([ADR-0014](0014-analysis-reuse-and-version.md)).

## 다시 볼 때

- 결정 로그 'LLM 제공자·모델 선택'이 정해질 때(실제 제공자 연결은 새 ADR로 남김)
- 비용 한도나 Kill Switch를 붙일 때
- 실제 제공자를 연결하기 전(실패한 분석의 호출 기록도 저장하도록 바꿀지)
