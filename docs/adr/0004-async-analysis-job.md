# ADR-0004: 분석은 비동기 작업으로 처리하고 상태는 허용 전이표로만 바꾼다

- 상태: 채택
- 결정한 날: 2026-10-21
- 관련: [PR #86](https://github.com/ShinhanDSProject/dart-insight/pull/86)(4.3), [PR #87](https://github.com/ShinhanDSProject/dart-insight/pull/87)(2.3), [PR #95](https://github.com/ShinhanDSProject/dart-insight/pull/95), 노션 개발 기준 3장, 화면 W-02

## 맥락

- 분석 하나는 재무제표·원문 받기, 원문 구조화, 재무·문장 비교, 요약(LLM)을 거쳐 수십 초에서 몇 분이 걸립니다. HTTP 요청 하나로 기다리면 시간 초과가 나고, 사용자가 다시 누르면 같은 분석이 여러 번 돕니다.
- 화면(W-02)은 진행 단계를 보여 줘야 합니다.
- 결과 일부만 저장된 채 '완료'로 보이면 근거 없는 화면이 나옵니다.

## 결정

- `POST /api/analyses`는 요청 안에서 비교 가능성 검증(2.2)만 합니다. 통과하지 못하면 422, 검증에 필요한 재무제표를 받지 못하면 502·503으로 끝납니다. 통과하면 분석을 만들어 ID를 바로 돌려줍니다(새로 만들었거나 진행 중이면 202, 완료된 결과를 다시 쓰면 200). 화면은 `GET /api/analyses/{analysisId}`로 상태와 단계를 조회하고, 완료되면 결과를 조회합니다.
- 상태는 `PENDING → RUNNING → COMPLETED` 또는 `FAILED`로만 바뀝니다. `AnalysisStatus`의 허용 전이표에 없는 전이는 거부합니다. 실패에는 사유 코드를 남깁니다.
- 결과(재무 수치·문장 변경·요약) 저장과 `COMPLETED` 표시는 한 트랜잭션입니다(`AnalysisResultService`). 저장하다 실패하면 완료가 되지 않습니다.
- 진행 단계(`AnalysisStep`: 요청 접수 → 보고서 비교 → 근거 확인 → 완료)는 앞으로만 갑니다.
- 실행은 서버 안의 대기열 있는 스레드 풀에서 합니다(`AnalysisRunner`). 대기열이 가득 차면 기다리지 않고 그 분석을 실패로 남깁니다.
- 같은 조건의 분석이 진행 중이면 새로 만들지 않고 그 분석을 돌려줍니다(조건별 잠금, 서버 한 대 기준). 서버가 다시 뜨면 끝나지 않은 분석을 실패로 바꿉니다. 같은 조건으로 다시 요청이 왔을 때 30분 넘게 상태가 바뀌지 않은 분석이 있으면 멈춘 것으로 보고 실패로 바꾼 뒤 새로 만듭니다(따로 돌며 정리하는 작업은 없음).

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 요청 하나에서 끝까지 기다리는 동기 API | 시간 초과와 재시도 때 분석이 중복됩니다. 진행 단계를 보여 줄 수 없습니다. |
| 메시지 큐(Kafka, RabbitMQ 등)와 별도 작업 서버 | 운영할 대상이 늘어 4주 MVP에는 큽니다. 서버 한 대에서는 스레드 풀로 충분합니다. |
| 상태를 자유롭게 바꾸는 setter | '완료인데 결과 없음', '실패 후 다시 진행' 같은 상태를 막을 수 없습니다. |
| 화면에 서버 푸시(WebSocket·SSE) | 상태 조회 주기가 몇 초여도 충분해, 연결 관리를 더할 이유가 없습니다. |

## 결과

- 좋아지는 점: 요청이 바로 끝나고, 화면이 단계를 보여 줍니다. 결과가 다 저장되지 않은 분석은 완료로 보이지 않습니다.
- 감수하는 점: 서버가 내려가면 진행 중인 분석은 실패로 끝나고 사용자가 다시 요청해야 합니다. 잠금이 서버 한 대 기준입니다.
- 지켜야 할 것: 상태는 허용 전이표를 거쳐서만 바꿉니다. 새 결과를 더하면 완료 표시와 같은 트랜잭션에서 저장합니다.

## 다시 볼 때

- 서버를 두 대 이상 띄울 때(잠금·대기열을 DB나 외부 큐로 옮겨야 함)
- 분석 대기열이 자주 가득 찰 때
