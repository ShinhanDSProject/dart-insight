# ADR-0036: 재무 설명 후보는 ai-server가 현재 보고서 문단 전체에서 글자 2개 단위 BM25로 찾는다

- 상태: 채택
- 결정한 날: 2026-10-27
- 관련: 이슈 [#146](https://github.com/ShinhanDSProject/dart-insight/issues/146), [AI 레이어 설계 v2](https://claude.ai/artifact/FTuyfxPRLHQiGszLWPa6GE) 4.1·4.5 2단계, [ADR-0015](0015-explanation-grade-and-quote-check.md)(후보 검색 위치를 바꿈. 등급·인용 결정은 그대로), 후속: #147(검색 방식 비교)·#148(벡터 검색)

## 맥락

- 지금은 backend `SummarySelector.candidates()`가 섹션 경로에 '경영진단'·'사업의내용'이 든 문단 중 검색어(`AccountAliases`)가 들어간 것을 **문서 순서대로 2개**(`CANDIDATES = 2`)만 골라 `POST /internal/summaries`에 보낸다. 순위가 없어 앞쪽의 덜 관련된 문단이 뽑히고, 다른 섹션(주석 등)의 설명은 보지 않는다.
- 로컬에서 SK하이닉스·삼성전자 등을 분석해 보니(2026-10-27), 사업의 내용의 '(3) 판매경로별 매출액 비중' 같은 목차 제목 줄이 매출액의 첫 후보가 되어 STATED 인용으로 쓰였다.
- 실제 보고서 6건(로컬 DB, 2024·2025 사업·반기보고서)의 현재 보고서 블록: 문단 490~760개, 4~7.5만 자(JSON 약 150~250KB). 표는 1,400~2,200개, 30~65만 자이고 표 하나가 11만 자인 것도 있다.
- 검색·색인 도구는 Python 쪽이 다양하고, 이후 벡터 검색(#148)도 ai-server에서 한다.
- 한국어 형태소 분석기 후보 `kiwipiepy` 0.24.1은 Windows·Linux 휠(abi3)이 있지만 모델 패키지(`kiwipiepy_model`)가 약 88MB다. M2 마감(2026-11-06)이 가깝고, CI와 시연 서버에 그만큼을 더 설치해야 한다.
- 검색어는 '매출액', '영업이익', '영업수익'처럼 띄어쓰기 없는 명사구다(ADR-0015의 계정명 정리 규칙과 표준계정 ID 사전).
- 실제 보고서 2건으로 잰 요청 크기와 시간(2026-10-27): SK하이닉스 2024 사업보고서 문단 601개 205KB, 색인 19ms·계정 4개 검색 1.9ms. 삼성전자 2026 반기보고서 문단 620개 217KB, 색인 17ms·검색 1.8ms.

## 결정

- **검색 위치**: 재무 설명 후보 검색을 backend에서 ai-server로 옮긴다. backend는 현재 보고서의 **문단(PARAGRAPH) 블록 전부**를 섹션 경로와 함께 `POST /internal/summaries` 요청의 `documentBlocks`로 한 번 보내고, 재무 항목에는 검색어(`accountAliases`)만 보낸다. 표 블록은 보내지 않는다. backend `SummarySelector.candidates()`는 없앤다.
- **후보 조건**(ai-server `app/summary/search.py`): 공백을 뺀 글에 검색어가 하나 이상 그대로 들어 있고, 공백을 뺀 길이가 40자 이상인 문단만 후보다(목차 제목·출처·안건 같은 짧은 줄을 빼기 위해. BM25는 짧은 글을 우대해, 20자 기준으로는 SK하이닉스(20250319000665) 매출액 1위가 '※ 출처: IDC 2024년 12월, 매출액 기준'이었고 40자로 올리자 경영진단의 '당사 매출액은 66조 1,930억원으로 …' 문단이 1위가 됐다. 60자도 결과가 같았다).
- **순위**: 후보 문단을 글자 2개 단위(공백을 뺀 글의 bigram)로 나눠 Okapi BM25(k1 = 1.5, b = 0.75)로 점수를 매기고, 섹션 가중치를 곱한다. 경로에 '경영진단'이 있으면 ×1.5, '사업의내용'이면 ×1.3, 그 밖은 ×1.0(잠정값, #147에서 조정). 점수가 같으면 문서 순서(블록 번호)가 앞선 것. 상위 5개(`CANDIDATE_LIMIT`)를 등급 판정(ADR-0015)에 넘긴다. 문단은 1,500자까지 쓴다.
- **BM25는 직접 구현한다**(라이브러리 없이 약 30줄). 색인은 요청마다 받은 문단으로 만들고 저장하지 않는다. 같은 입력이면 같은 후보가 같은 순서로 나온다.
- **후보가 0개**인 재무 항목은 지금처럼 LLM에 묻지 않고 `NONE`이다. backend는 문장 변화 항목도 문단 블록도 없으면 ai-server를 부르지 않는다.
- **근거 확인**: backend는 재무 설명의 근거·인용 위치가 **보낸 문단 블록**의 근거 ID(`{접수번호}#B{블록 번호}`)인지 확인한다(지금은 '그 항목에 보낸 후보'). ai-server는 그 항목에서 고른 후보 안에서만 근거를 허용한다(ADR-0015 그대로).
- **검색어 사전은 backend에 둔다**(`AccountAliases`). ADR-0015는 "검색을 ai-server로 옮길 때 사전도 함께 옮긴다"고 했지만, 사전은 표준계정 ID를 키로 하고 그 ID는 backend의 재무 결과에만 있다. 이번에는 검색만 옮기고 사전은 `accountAliases`로 계속 보낸다.
- 결과가 달라지므로 backend `Analysis.CURRENT_VERSION`을 올린다([ADR-0014](0014-analysis-reuse-and-version.md)).

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 형태소 분석기(`kiwipiepy`) + BM25 | 조사를 떼는 정확도는 낫지만 모델이 약 88MB라 CI·시연 서버 설치가 무거워진다. 검색어가 띄어쓰기 없는 명사구라 글자 2개 단위로도 '매출액은'·'매출액이' 같은 꼴을 찾는다. 정답 자료로 두 방식을 비교하는 일은 #147에서 한다. |
| `rank_bm25` 라이브러리 | numpy가 필요하고 2022년 이후 갱신이 없다. 식이 짧아 직접 쓰는 편이 의존성 없이 결과를 그대로 재현하기 쉽다. |
| backend(Java)에서 BM25로 바꾸고 후보만 계속 보내기 | 요청은 작게 유지되지만, 검색을 ai-server로 모으는 설계(벡터 검색 #148, 검색 방식 비교 #147)와 어긋나 같은 일을 두 언어로 하게 된다. |
| 표 블록까지 보내기 | 보고서 하나에 30~65만 자라 요청이 커지고, 지금도 표는 후보로 쓰지 않는다. 표 검색은 따로 필요해질 때 정한다. |
| 섹션 제한(경영진단·사업의 내용) 유지 | 주석 등 다른 섹션의 설명을 계속 놓친다. 대신 두 섹션은 가중치로 먼저 본다. |

## 결과

- 좋아지는 점: 관련도 순으로 후보를 골라 앞쪽의 덜 관련된 문단이 밀어내는 일이 줄고, 다른 섹션의 설명도 후보가 된다. 짧은 목차 줄이 인용되지 않는다. 새 의존성이 없다.
- 감수하는 점: 요약 요청이 보고서마다 약 150~250KB 커진다. 재무 항목마다 후보가 2개에서 최대 5개로 늘어 LLM 입력 토큰이 는다. 글자 2개 단위는 형태소 분석보다 엉뚱한 겹침이 있을 수 있어 '검색어가 그대로 든 문단' 조건으로 막는다.
- 지켜야 할 것: 후보 조건·가중치·`CANDIDATE_LIMIT`를 바꾸면 backend `Analysis.CURRENT_VERSION`을 올린다. 근거 ID는 backend가 보낸 블록의 것만 쓴다. 검색어 사전은 backend 한 곳에서만 고친다.

## 다시 볼 때

- #147에서 정답 자료로 검색 방식(글자 2개 단위·형태소·벡터)을 비교한 결과가 나올 때
- 벡터 검색(#148)을 채택하거나 이전 보고서까지 검색할 때
- 요약 요청 크기나 LLM 비용이 문제가 될 때
