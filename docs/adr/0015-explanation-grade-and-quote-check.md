# ADR-0015: 재무 설명은 등급·인용과 함께 내고, 코드가 인용을 확인해 등급을 낮춘다

- 상태: 채택
- 결정한 날: 2026-10-23
- 관련: 이슈 [#141](https://github.com/ShinhanDSProject/dart-insight/issues/141)·[#142](https://github.com/ShinhanDSProject/dart-insight/issues/142)·[#143](https://github.com/ShinhanDSProject/dart-insight/issues/143), [AI 레이어 설계 v2](https://claude.ai/artifact/FTuyfxPRLHQiGszLWPa6GE) 3장·4.5~4.9, 기능 기획서 '재무 변화의 회사 설명을 근거 등급과 함께 보여 주기'(FS 번호 미정), 대체: [ADR-0012](0012-grounded-summary.md)

## 맥락

- [ADR-0012](0012-grounded-summary.md)는 재무 설명을 '있다/없다' 두 가지로만 냅니다(`summary_item.explanation_status` = `FOUND`·`NOT_FOUND`·`REVIEW_NEEDED`). 회사가 변화의 원인을 직접 밝힌 문단과, 관련은 있지만 원인을 말하지 않은 문단을 구분하지 못해, 관련 문단을 원인처럼 쓴 문장이 나갈 수 있습니다.
- 설명 후보는 `SummarySelector.candidates()`가 공백만 뺀 계정명(`account_nm`)을 문단에서 그대로 찾습니다. 2024 사업보고서 5건(연결)으로 확인한 결과(2026-10-23):
  - SK하이닉스(20250319000665)·카카오(20250324000901)는 계정명이 `영업이익(손실)`·`당기순이익(손실)`이라 경영진단·사업의 내용에서 후보가 0개입니다. 본문에는 '영업이익'이 각각 5문단·1문단 있습니다.
  - 같은 표준계정이라도 계정명이 회사·연도마다 다릅니다. `dart_OperatingIncomeLoss` = 영업이익 / 영업이익(손실) / 영업손실(LG디스플레이 20250312000906), `ifrs-full_Revenue` = 매출액 / 매출 / 영업수익.
  - 본문은 재무상태표 합계를 '자산총액'·'부채총액'·'총자산'으로도 씁니다.
- 지금은 문서 순서 앞의 2개만 후보로 쓰므로(`SummarySelector.CANDIDATES`), 설명이 아닌 문단을 잡는 검색어를 넣으면 진짜 설명 문단이 밀려납니다.
- 의미 수준의 인용 검증(NLI·LLM 판정)은 MVP에서 빼고 확장 1순위로 뒀습니다(ADR-0012 관련 결정 로그). 이 결정의 인용 확인은 글자 비교이고, 그 결정을 바꾸지 않습니다.
- LLM 제공자는 아직 정하지 않았습니다(#50). 등급 판정 품질은 실제 모델을 연결해야 볼 수 있고, 코드 규칙은 가짜 제공자로 검증합니다([ADR-0008](0008-single-llm-module.md)).
- M2 마감(2026-11-06)까지 남은 기간이 짧아, 초기 설계(10/21)의 Tool Calling 설명 탐색 에이전트 대신 고정 검색과 단발 판정으로 합니다(설계 v2 6장).

## 결정

ADR-0012의 결정 중 아래 두 가지(설명 후보, 재무 설명의 출력과 검증)를 바꾸고, 나머지는 그대로 이어 갑니다.

**그대로 이어 가는 것**

- 요약할 변화는 backend `SummarySelector`가 규칙으로 고른다(재무 수치 손익계산서 3개·재무상태표 2개, 문장 변화는 우선순위 높음·중간 상위 5개). 설명 후보는 현재 보고서의 경영진단·사업의 내용 문단 중 앞의 2개다.
- 재무 수치의 사실 문장은 backend `FinancialFacts`가 코드로 쓴다. 숫자는 계산한 값을 그대로 쓰고 '늘었어요·줄었어요'로만 적는다.
- 문장 변화 항목은 지금처럼 LLM이 무엇이 바뀌었는지 한 문장으로 쓴다. 등급을 매기지 않는다.
- ai-server는 근거 ID가 후보 위치인지, 숫자·크기 표현이 인용한 원문에 있는지, 투자 권유성 표현이 없는지([ADR-0013](0013-expression-check-gate.md)) 검증하고, 실패하면 최대 2회 다시 생성한다. backend는 응답의 근거 ID를 다시 확인한다. ai-server·LLM을 부를 수 없으면 분석을 실패로 끝낸다.
- 'AI 생성' 표시는 응답 값으로 코드가 붙이고, 모델·프롬프트 버전·생성 시각과 LLM 호출 기록을 저장한다.

**바꾸는 것 1: 설명 후보 검색어**

- 검색어는 계정명 그대로가 아니라 표준계정 ID(`account_id`)를 키로 한 사전과 계정명 정리 규칙으로 만든다. 사전은 backend 한 곳에 두고(`com.dartinsight.summary` 패키지), 실제 공시의 설명 문장에서 확인한 표현만 넣는다.
- 계정명 정리 규칙: `X(Y)` 꼴은 X와 Y를 각각 검색어로 쓴다. 계정명과 정리 규칙에서 나온 2글자 이하 검색어는 버린다. 사전에 든 말은 길이와 관계없이 쓴다. 표준계정 ID가 없는 계정(`-표준계정코드 미사용-`)은 정리 규칙만 쓴다.
- backend는 만든 검색어를 `POST /internal/summaries` 재무 항목에 함께 보낸다(`accountAliases`). ai-server는 검색어를 만들지 않고 받은 것을 검증에 쓴다.

**바꾸는 것 2: 재무 설명의 등급과 인용**

- LLM은 설명 후보가 있는 재무 항목마다 등급(`STATED` 회사가 직접 밝힘 · `RELATED` 관련 내용 있음 · `NONE` 확인된 설명 없음), 인용문(`quote`), 인용 위치(`quoteEvidenceId`)를 JSON으로 낸다. 처음에는 지금의 요약 호출 출력 스키마(`ai-server/app/summary/prompt.py` `OUTPUT_SCHEMA`)에 필드를 더하고, 품질이 부족하면 별도 호출로 나눈다(새 ADR 불필요, `PROMPT_VERSION`만 올림).
- ai-server `app/summary/validate.py`가 등급을 낮춘다. 올리는 규칙은 없다.
  - 인용 위치가 넘겨준 후보 위치가 아니거나, 인용문이 공백 정규화 뒤 그 문단에 그대로 없으면 `NONE`
  - 인용문에 `accountAliases`의 검색어가 하나도 없으면 `RELATED`까지
  - 낮출 때는 다시 생성하지 않고, 낮춘 사유를 `reviewReason`에 남긴다
- 원인 표현(때문, 로 인해, 에 기인 등 명백한 인과만)은 `STATED` 설명에만 허용한다. `STATED`가 아닌 설명에 있으면 다시 생성한다(최대 2회, 그래도 남으면 '검토 필요'). 규칙은 `app/summary/` 아래에 [ADR-0013](0013-expression-check-gate.md)의 표현 검사와 같은 틀(규칙 ID, 정규식 상수, 버전 상수)로 둔다. 화면 노출 규정이 아니라 등급 규칙이므로 `app/compliance/`에 두지 않는다.
- 후보가 0개인 항목은 지금처럼 LLM을 부르지 않고 `NONE`이다.
- backend는 등급·인용·인용 위치를 `summary_item`의 새 컬럼(`explanation_grade`, `quote`, `quote_evidence_id`, 새 Flyway 마이그레이션)에 저장한다. `explanation_status`는 처리 결과로 그대로 두고, `NOT_FOUND`는 `NONE`과 같은 뜻으로 `docs/erd.md`에 대응을 적는다.
- 화면은 등급별 문구를 쓴다: `STATED` "회사는 공시에서 ~라고 설명함" + 인용·위치, `RELATED` "관련 공시 내용" + 인용·위치, `NONE` "확인된 설명 없음". 코드가 낮춘 `NONE`은 후보가 없던 경우와 다른 사유 문구로 보인다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 지금처럼 두 단계(설명 있음/없음)를 두고 프롬프트에 "원인을 지어내지 말라"만 더하기 | 원인처럼 쓴 문장을 코드가 잡을 방법이 없습니다. 인용이 원문에 있는지도 확인하지 않습니다. |
| 초기 설계의 Tool Calling 설명 탐색 에이전트(최대 4회 반복) | 검색 대상이 보고서 하나라 고정 검색 + 단발 판정으로 같은 결과를 더 싸고 일정하게 얻습니다. 반복 횟수에 따라 결과와 비용이 흔들립니다. |
| 인용이 주장을 뒷받침하는지 NLI·LLM으로 판정 | MVP에서 뺀 확장 1순위 항목이고 일정상 어렵습니다. 글자 비교로 인용 실재와 항목명만 확인하고, 부족하면 설명 검토(보류)를 붙입니다. |
| 동의어 사전을 계정명으로 찾기 | 같은 회사도 손실인 해에 계정명이 '영업손실'로 바뀌어 사전에서 찾지 못합니다. 표준계정 ID는 이름이 바뀌어도 같습니다. |
| 검색어 사전을 ai-server에 두기 | 후보 검색이 backend `SummarySelector`에 있어 사전도 같은 곳에 두어야 한 번만 관리합니다. 검색을 ai-server로 옮길 때(#146) 함께 옮깁니다. |
| 기존 `explanation_status` 값을 `STATED`·`RELATED`·`NOT_FOUND`·`REVIEW_NEEDED`로 바꾸기 | 처리 상태와 설명 성격이 한 값에 섞이고, `FOUND`를 쓰는 backend·frontend 코드를 모두 고쳐야 합니다. |

## 결과

- 좋아지는 점: 회사가 직접 밝힌 이유만 원인으로 보입니다. 인용문이 실제 원문에 있는지 코드가 확인합니다. 계정명 표기 차이로 설명 후보를 놓치는 경우가 줄어듭니다(위 5건에서 SK하이닉스·카카오의 0개가 해소됨).
- 감수하는 점: 등급 판정 자체는 LLM이 하므로, 인용이 원인을 말하는지(STATED와 RELATED의 경계)는 코드가 확인하지 못합니다. 원인 표현 목록은 좁게 시작해서 간접 인과("~에 따라", "기여")는 통과합니다. 사전은 손으로 관리하며, 확인하지 않은 회사의 표현은 빠질 수 있습니다. 출력 필드가 늘어 형식 오류로 다시 생성하는 경우가 늘 수 있습니다.
- 지켜야 할 것: 사전·정리 규칙·강등 규칙·원인 표현 목록·프롬프트를 결과가 달라지게 바꾸면 `PROMPT_VERSION`(또는 해당 규칙 버전)과 backend `Analysis.CURRENT_VERSION`을 함께 올립니다([ADR-0014](0014-analysis-reuse-and-version.md)). 사전에는 실제 공시에서 확인한 표현만 넣고, 확인한 접수번호를 테스트 자료로 남깁니다. 등급은 정기보고서 근거로만 매깁니다.

## 다시 볼 때

- 실제 LLM 제공자를 연결해 등급 판정 품질을 평가할 때(#50, 7.3)
- 평가용 정답 자료(#56)로 등급 오류나 원인 표현 누락이 많다고 확인될 때(설명 검토 추가, 목록 확대)
- 설명 후보 검색을 ai-server로 옮기거나(#146) 벡터 검색을 채택할 때(#147, #148)
- 수시공시를 근거로 붙일 때(#24)
