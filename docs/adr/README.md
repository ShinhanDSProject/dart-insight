# 아키텍처 결정 기록(ADR)

구조에 영향을 주는 결정을 왜 그렇게 했는지 남깁니다. 코드는 무엇을 했는지 보여 주지만, 왜 그렇게 했고 무엇을 버렸는지는 보여 주지 않습니다. 이유가 남아 있지 않으면 몇 주 뒤에 같은 논의를 다시 하거나, 이유를 모른 채 규칙을 깨기 쉽습니다. AI 코딩 도구도 이 기록을 읽고 따릅니다([`AGENTS.md`](../../AGENTS.md)).

## 무엇을 ADR로 남기나

아래 중 하나에 해당하는 결정을 하면 ADR을 씁니다.

- 서비스 사이의 책임이나 호출 방향을 정하거나 바꿈 (예: 원문 파싱을 어느 서비스가 맡나)
- 데이터를 저장하는 방식, 키, 스키마 관리 방식을 정함
- 외부 서비스(OpenDART, LLM 제공자)와 연동하는 방식을 정함
- 비동기 처리, 상태 관리, 재시도·시간 제한·캐시 같은 동작 방식을 정함
- 여러 서비스가 함께 지키는 규약(에러 형식, 추적 ID, 근거 ID, 버전)을 정함
- 프레임워크·라이브러리·알고리즘을 고르는데, 나중에 바꾸기 어렵거나 분석 결과가 달라짐
- 채택된 ADR과 다르게 만들어야 함 (새 ADR을 써서 이전 ADR을 대체)

ADR로 남기지 않는 것:

| 이런 결정은 | 여기에 남깁니다 |
| --- | --- |
| 기획·범위·우선순위, 화면 문구, 판단 기준(비교 기준, 금지 표현 목록 등), 팀 운영 규칙(키 관리, 병합 방식 등) | 노션 [결정 로그](https://app.notion.com/p/4ce942f6c0bc4d77a490ceeda26d4a18) |
| 이슈 안에서 끝나는 구현 세부(함수 나누기, 이름, 작은 리팩터링) | PR 본문 |
| API 경로·필드, 테이블·컬럼 자체 | [`docs/api-spec.md`](../api-spec.md), [`docs/erd.md`](../erd.md) (ADR에는 왜 그렇게 했는지만) |

판단이 어려우면 "몇 달 뒤 누군가 이 코드를 보고 이유를 몰라 되돌릴 수 있나"를 물어봅니다. 그렇다면 ADR을 씁니다. 결정 로그의 결정이 구조를 바꾸면(예: LLM 제공자를 정함) 그 구조 변경을 ADR로 쓰고 결정 로그 항목을 링크합니다.

## 쓰는 법

1. [`docs/templates/adr.md`](../templates/adr.md)를 복사해 `docs/adr/{번호 4자리}-{짧은-영문-이름}.md`로 만듭니다. 번호는 아래 목록의 다음 번호입니다.
2. 결정을 구현하는 PR에 ADR을 함께 넣고 상태를 '채택'으로 둡니다. 구현 전에 팀 합의가 먼저 필요하면 상태를 '제안'으로 두고 문서 PR을 먼저 올린 뒤, 병합할 때 '채택'으로 바꿉니다.
3. 아래 목록에 한 줄을 더합니다.
4. PR 본문의 'ADR' 항목에 추가하거나 대체한 ADR 번호를 적습니다.

여러 PR이 동시에 같은 번호를 쓰면 나중에 병합하는 쪽이 번호를 올립니다.

## 고치는 법

- 채택된 ADR의 결정은 고치지 않습니다. 결정을 바꾸려면 새 ADR을 쓰고, 이전 ADR은 상태 줄만 '대체됨(ADR-NNNN)'으로 바꿉니다. 결정을 그만두기만 하면 '폐기'로 바꾸고 이유를 한 줄 더합니다.
- 오타, 링크, 바뀐 파일 경로처럼 결정과 상관없는 내용은 고쳐도 됩니다.
- 이미 있는 코드를 소급 기록한 ADR(0002~0014)이 그 코드와 다르게 적혀 있으면, 결정을 바꾸는 것이 아니라 기록을 바로잡는 것이므로 코드에 맞춰 고칩니다. 코드 쪽을 바꾸고 싶다면 새 ADR을 씁니다.
- ADR의 '다시 볼 때'에 적은 조건이 생기면(예: 결정 로그의 잠정 항목이 정해짐) 새 ADR이 필요한지 검토합니다.
