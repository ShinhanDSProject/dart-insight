# ADR-0025: AI 기업 브리핑은 최신 사업보고서의 정해진 항목에서 근거를 골라 동기로 만들고, 보고서·프롬프트 버전마다 한 번만 저장한다

- 상태: 채택
- 결정한 날: 2026-10-26
- 관련: #333, 노션 기능 기획서 FS-49 '근거와 함께 보는 AI 기업 브리핑', ADR-0003·0008·0009·0013·0014·0023

## 맥락

- 기업 화면 개요 탭 맨 위에 회사가 무엇을 하는지, 주요 제품·매출 구성, 회사가 밝힌 위험을 5줄 안팎으로 보여 주고 싶다(FS-49). 분석(두 보고서 비교)과 달리 보고서 하나, 기업 하나에 대한 글이다.
- AGENTS.md AI 규칙: LLM은 `app/llm` 한 모듈로만 부르고, 계산을 맡기지 않으며, 문장마다 저장된 원문 위치의 근거 ID가 있어야 하고, 검증 실패는 2회까지 다시 만든 뒤 '검토 필요'로 끝낸다. 표현 검사(ADR-0013)를 거치고, 'AI 생성' 표시와 모델·프롬프트 버전·생성 시각을 저장한다.
- 원문은 접수번호 기준으로 받아 구조화해 둔다(`DocumentService.ensureStructured`, ADR-0003·0009). 근거 ID는 `{접수번호}#B{블록 번호}`다.
- 질문 답변(ADR-0023)이 이미 같은 일을 한다: backend가 후보 문단을 골라 보내고, ai-server가 인용·숫자·표현을 검증한다. 동기 호출이다.
- 정기보고서 'II. 사업의 내용'은 하위 목차가 정해져 있다(1. 사업의 개요, 2. 주요 제품 및 서비스, … 4. 매출 및 수주상황, 5. 위험관리 및 파생거래 …). 사업보고서에 '위험 요인' 목차는 따로 없다.
- 처음 보는 보고서는 원문 받기·구조화(수 초~수십 초)와 LLM 호출(재생성 포함 최대 3번)을 거친다. 한 번 만들면 같은 보고서에 대해 다시 만들 이유가 없다.

## 결정

- **호출 방식**: `GET /api/companies/{corpCode}/briefing`은 동기 호출이다. 저장된 브리핑이 있으면 그대로 돌려주고, 없으면 그 요청 안에서 만들고 저장한 뒤 돌려준다. 분석처럼 작업 ID·폴링을 두지 않는다(ADR-0023과 같은 이유: 한 번 호출로 끝나고, 실패하면 다시 열면 된다). 대기 시간은 AI 서버 호출 대기 시간(`app.ai-server.read-timeout`)을 따른다. 화면은 '만드는 중' 상태를 보여 준다.
- **원문 보고서**: 그 기업 정기보고서 목록(`ReportService.list`, 4.1 캐시 규칙)에서 대상 기간이 가장 최근인 사업보고서, 없으면 가장 최근 정기보고서. 원문은 `DocumentService.ensureStructured`로 준비한다(접수번호 캐시 재사용).
- **근거 고르기(backend `BriefingSources`)**: 구조화한 원문에서 제목에 '사업의 내용'이 든 대목차를 찾고, 그 아래 하위 목차 제목으로 주제를 정한다: 개요(`사업의 개요`), 주요 제품(`주요 제품`), 매출(`매출`), 위험(`위험관리`, 모자라면 대목차 `투자자 보호`). 주제마다 문단 먼저, 모자라면 표로 최대 2개, 모두 8개까지 보낸다. 짧은 문단(40자 미만, 소제목)은 빼고, 글은 2,000자까지 자른다. 하위 목차를 못 찾으면 '사업의 내용' 아래 앞 문단 3개를 개요로 쓴다. 후보가 없으면 ai-server를 부르지 않고 `NOT_AVAILABLE`이다(저장하지 않음).
- **문장 만들기(ai-server `POST /internal/briefings`)**: 원문은 `<disclosure id topic sectionPath>` 태그로 감싸 자료로만 쓴다. LLM 출력은 `{"sentences": [{"text", "evidenceIds"}]}`이고, 검증(`app/briefing/validate.py`)은 문장 1~6개, 문장마다 보낸 근거 ID가 하나 이상, 숫자·크기 표현이 인용한 원문에 있음(`app.llm.grounding`), 원인 표현은 인용 원문에도 있을 때만, 표현 검사(5.5) 통과다. 하나라도 어기면 문제를 알려 주며 2회까지 다시 만들고, 끝내 실패하면 문장 없이 `REVIEW_NEEDED`다(일부 문장만 내보내지 않는다).
- **프롬프트 버전**: backend `BriefingService.PROMPT_VERSION`과 ai-server `app/briefing/prompt.py`의 `PROMPT_VERSION`을 같게 둔다. backend가 요청에 버전을 넣고, ai-server는 다르면 400으로 거절한다(버전이 어긋나 매번 새로 만드는 일을 막음). 프롬프트·근거 고르기 규칙을 바꾸면 두 곳을 같은 PR에서 올린다.
- **저장**: `company_briefing`에 접수번호·프롬프트 버전(UNIQUE)·상태·문장과 근거(접수번호·섹션·블록·섹션 경로·인용 글, JSON)·모델·생성 시각·추적 ID를 둔다. `GENERATED`·`REVIEW_NEEDED` 모두 저장해 같은 보고서·프롬프트 버전이면 다시 만들지 않는다. LLM 호출 기록은 `llm_call`(task `briefing`)에 남긴다. 분석에 속하지 않으므로 `llm_call.analysis_id`를 null 허용으로 바꾸고 `company_briefing_id`를 더한다(`V23__create_company_briefing.sql`).
- **같은 요청이 겹칠 때**: 접수번호별 잠금(서버 한 대) 안에서 다시 확인하고 만들며, 그래도 UNIQUE에 걸리면 저장된 것을 돌려준다.
- **화면**: 'AI 기업 브리핑' 카드에 'AI 생성' 배지, 원문 보고서 이름·DART 링크, 문장마다 근거 버튼(누르면 섹션 경로와 인용 문단)을 둔다. `REVIEW_NEEDED`는 '검토 필요', `NOT_AVAILABLE`은 그 사유를 보여 준다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 비동기 작업(작업 ID·폴링) | 보고서마다 한 번만 만들고 그 뒤엔 저장된 것을 바로 준다. 상태 표·전이표·폴링 화면을 더 만드는 비용이 크다. 처음 한 번 느린 것은 로딩 상태로 견딘다 |
| 보고서 목록을 받을 때 미리 만들기 | 보지 않을 기업까지 LLM 비용이 든다 |
| 낱말 검색(ADR-0023 `QuestionRetriever`)으로 후보 찾기 | 브리핑은 질문이 없다. 정기보고서 목차가 정해져 있어 제목으로 고르는 편이 예측 가능하다 |
| 검증을 통과한 문장만 골라 내보내기 | 몇 줄만 남으면 회사 소개가 한쪽으로 치우칠 수 있다. 다시 만들어도 실패하면 통째로 '검토 필요'로 둔다 |
| `llm_call`에 넣지 않고 브리핑 표에 호출 수만 두기 | AI 사용 현황(0.7)이 모든 LLM 호출을 한 표에서 센다. 비용 집계가 갈라진다 |
| backend가 매번 ai-server에 프롬프트 버전을 묻기 | 저장된 브리핑을 보여 줄 때도 ai-server가 필요해진다 |

## 결과

- 좋아지는 점: 기존 원문 캐시·구조화·LLM 모듈·검증·표현 검사를 그대로 쓴다. 같은 보고서는 한 번만 비용이 든다.
- 감수하는 점: 처음 여는 기업은 수 초~수십 초 기다린다. 목차 제목이 다른 보고서(예전 양식)는 근거를 덜 찾을 수 있다. `REVIEW_NEEDED`도 저장하므로 프롬프트 버전을 올리기 전에는 다시 만들지 않는다.
- 지켜야 할 것: 브리핑 문장의 숫자는 인용한 원문에 있어야 한다. 근거 ID는 보낸 블록 안에서만 쓴다. backend·ai-server 프롬프트 버전을 함께 바꾼다.
