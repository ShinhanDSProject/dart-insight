# ADR-0057: 주요 사건 호출은 다른 LLM 작업과 따로 제한시간과 출력 한도를 두고, 2.12 측정값에 맞춘다

- 상태: 채택 (금액 예산을 넘긴 사건의 처리는 ADR-0058이 대체)
- 결정한 날: 2026-11-05
- 관련: 이슈 #714(2.17), 측정 결과 #641(2.12), [ADR-0050](0050-text-events-after-analysis.md)(제한시간 가정을 대체), [ADR-0051](0051-text-event-candidate-rules.md), [ADR-0053](0053-event-scale-amount-candidates.md)

## 맥락

ADR-0050은 제한시간을 2.12에서 정하기로 하고 backend 대기 시간만 300초로 가정했다. 2.12에서 `gpt-6.1-sol`로 세 기업을 잰 값은 다음과 같다(재시도 없는 경우).

| 기업 | 묶기 입력·출력 토큰 | 묶기 호출 | 금액 고르기 호출 | 금액 고르기 시간(어림) | 전체 |
| --- | --- | --- | --- | --- | --- |
| 고려아연 | 64,487 / 12,131 | 99초 | 23번 | 약 80초 | 180초 |
| 삼성전자 | 78,439 / 18,610 | 148초 | 30번 | 약 165초 | 313초 |
| SK하이닉스 | 62,676 / 13,774 | 102초 | 16번 | 약 95초(절전 제외) | 약 196초(절전 제외) |

- 새 값으로 삼성전자를 다시 재니 묶기 출력 21,966, 묶기 호출 162초, 금액 고르기 29번(호출당 최대 4초), 전체 233.5초, 사건 92건이었다. 같은 입력이어도 실행마다 값이 달라진다.
- 제품 기본값은 호출당 60초, 요청 전체 120초(`LlmSettings`), 묶기 출력 16,000(`app/events/prompt.py`), backend 300초(`text-events-read-timeout`)다. 이 값으로는 세 기업의 묶기 호출이 모두 시간 초과이고, 삼성전자는 출력도 잘린다. 실제로 삼성전자는 한도 16,000에서 `max_output_tokens` 오류로 실패했다.
- 호출당·요청 전체 제한시간은 요약, 설명, 채팅이 함께 쓴다. 요약 등은 backend가 180초 기다리므로 `LLM_*` 값을 통째로 올릴 수 없다.
- 금액 고르기 호출 하나가 약 12분(729초) 걸린 것은 PC 절전 때문이다. Windows 기록에 16:55:35 절전 시작, 17:07:50 해제(735초)가 있다. 서비스 문제로 다루지 않는다.
- 호출당 제한시간은 호출 전체가 아니라 네트워크 읽기 한 번의 제한이다. 로컬 가짜 서버로 재니, 응답이 아예 없으면 제한 2초에 2.2초로 끝났고, 1초마다 조금씩 보내면 8초까지 갔다. 2.12에서 이런 응답은 보지 못했다.

## 결정

**요청마다 제한시간을 줄 수 있게 한다.** `LlmRequest`에 `timeout_seconds`, `total_timeout_seconds`(기본 None)를 더하고, `LlmClient`는 값이 있으면 설정 대신 쓴다. 다른 작업은 값을 주지 않으므로 그대로다.

**값은 코드 상수로 둔다.**

| 어디 | 값 | 이유 |
| --- | --- | --- |
| 묶기 호출 제한(`app/events/prompt.py`) | 240초 | 측정 최대 148초의 약 1.6배 |
| 묶기 요청 전체(같은 파일) | 480초 | 호출 2번이 들어가는 시간. 검증 재생성을 끝까지 다 하지 못할 수 있다 |
| 묶기 출력 한도(같은 파일) | 32,000 | 측정 최대 18,610의 약 1.7배 |
| 금액 고르기 전체 예산(`app/events/scales.py`) | 240초 | 측정 최대 약 165초. 넘으면 남은 사건은 AI를 부르지 않고 ADR-0053의 규칙으로 정한다 |
| 금액 고르기 호출 하나 | 그대로(호출당 60초, 전체 120초) | 평소 약 9초 이내 |
| backend `text-events-read-timeout` | 900초 | 최악 480 + 240 + 120 = 840초보다 길어야 호출 기록이 backend로 돌아온다 |

**나눠 부르기는 하지 않는다.** ADR-0050 가정 2는 그대로 두고, 측정 입력(최대 7.8만 토큰)이 한 번에 들어가므로 구현하지 않는다.

**호출 전체를 끊는 시계는 두지 않는다.** 조금씩 오는 응답은 보지 못했고, 끊으려면 호출을 스레드로 감싸야 해서 값보다 복잡해진다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| `LLM_TIMEOUT_SECONDS`·`LLM_TOTAL_TIMEOUT_SECONDS`를 전체로 올리기 | 요약 등의 실패가 늦게 드러나고 backend 180초를 넘어 호출 기록이 돌아오지 않습니다. |
| 환경변수로 사건 값을 따로 두기 | 바꿀 일이 2.19와 7.7 측정 때뿐이고, 설정이 늘어납니다. 측정값과 이유를 코드 옆에 두는 편이 낫습니다. |
| 후보를 나눠 묶고 합치기 | 시간과 출력은 줄지만 호출이 늘고, 나뉜 곳에서 사건이 쪼개지며 합치는 호출과 검증이 더 필요합니다. 2.19로 사건 수를 줄이면 필요 없을 수 있습니다. |
| 스트리밍으로 받기 | 묶기 응답은 전체를 받아야 검증할 수 있어 얻는 것이 적고, `LlmClient`와 제공자 양쪽을 바꿔야 합니다. |

## 결과

- 좋아지는 점: 세 기업 규모의 사건 만들기가 시간 초과나 출력 잘림 없이 끝날 수 있습니다. 다른 LLM 작업은 그대로입니다.
- 감수하는 점: 사건 하나의 실행이 최악 15분 가까이 backend 스레드(최대 4개)를 잡습니다. 실행 한 번의 출력 비용 상한이 올라갑니다. 묶기 요청 전체 480초로는 검증 재생성 2회를 끝까지 하지 못할 수 있고, 그때는 `LlmOutputInvalid`로 끝납니다. 금액 예산을 넘긴 사건은 규칙으로 정해 정확도가 떨어질 수 있습니다.
- 지켜야 할 것: ai-server 쪽 시간을 올리면 backend `text-events-read-timeout`이 그 합보다 긴지 함께 봅니다.

## 다시 볼 때

- 2.19로 사건 수가 줄거나 모델을 바꿔, 측정값이 크게 달라질 때
- 7.7에서 시간 초과나 출력 잘림이 다시 나올 때
- 조금씩 오는 응답으로 호출이 제한시간을 넘기는 일이 실제로 생길 때
