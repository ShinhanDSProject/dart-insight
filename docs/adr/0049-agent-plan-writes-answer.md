# ADR-0049: 에이전트의 Tool 고르기가 자료가 충분하다고 판단하면 같은 호출에서 답 초안까지 쓰고, 검토는 그대로 거친다

- 상태: 채택
- 결정한 날: 2026-11-04
- 관련: #632, [ADR-0045](0045-langgraph-agent-step-graph.md)의 일부를 대체(그래프의 '자료 충분 → draft_answer' 부분과 '검토 노드를 거치지 않은 답을 내보내지 않는다' 문장. LangGraph 도입 범위·재생성 예산·쓰지 않는 기능 등 나머지 결정은 ADR-0045 그대로), [ADR-0044](0044-agent-tools-run-in-backend.md), #631(정해진 요청), #633(Tool 고르기 측정)

## 맥락

- ADR-0045는 한 단계를 `route_intent → plan_next_tool → (자료 충분) draft_answer → review_answer`로 정했다. `plan_next_tool`이 '자료 충분'이라고 답하면 `draft_answer`가 LLM을 한 번 더 불러 답을 쓴다.
- 실측(2026-11-04, gpt-6.1-sol, 채팅 39건): Tool 고르기 평균 3.1초·입력 4.9천 토큰, 답 쓰기 평균 7.0초·입력 5.9천 토큰. 가장 흔한 채팅(13건)은 'Tool 고르기 → 충분 판단 고르기 → 답 쓰기' 3번 호출로 LLM 시간만 11.6초였다. 가운데 '충분' 판단 호출은 결정 하나(출력 수십 토큰)를 위해 Tool 목록과 받은 결과 전체를 다시 보낸다.
- 두 호출은 같은 입력(질문·대화·Tool 결과)을 받는다. 답 쓰기는 여기에 답 규칙과 답 형식(스키마)이 더해질 뿐이다.
- 답 검사(근거 ID, 숫자, 원인 표현, 등급, 표현 검사)는 코드 규칙인 `review_answer`가 맡고, 재생성 예산은 '처음 1 + 다시 2'다(ADR-0045). 이 둘은 바꾸지 않아야 한다.
- #631에서 정해진 요청(이동·저장 확인)은 `route_intent`가 LLM 없이 정해진 안내로 답한다. ADR-0045의 '검토 노드를 거치지 않은 답을 내보내지 않는다'와 글자로는 어긋나므로 여기서 함께 정리한다.

## 결정

- **Tool 고르기 출력에 답 초안을 둔다.** `plan_next_tool`의 구조화 출력(`app/agent/prompt.py` `plan_schema`)에 `draft`를 더한다. `decision`이 `ANSWER`이면 `draft`에 답 초안(`answer_schema`와 같은 꼴: `status`·`answer`·`evidenceIds`·`actions`)을 쓰고, `CALL_TOOLS`이면 `draft`는 null이다. 계획 프롬프트(`PLAN_SYSTEM`)에 답 규칙(지금 `ANSWER_SYSTEM`의 규칙)을 함께 넣는다.
- **그래프**

  ```
  route_intent ─┬─ OUT_OF_SCOPE / 정해진 요청(LLM 없음) / 빠른 명령 ──────────→ build_response
                └─ plan_next_tool ─┬─ CALL_TOOLS ──────────────────────────────→ build_response
                                   ├─ ANSWER + draft ──→ review_answer ─┬─ 통과 ──→ build_response
                                   │                        ↑           └─ 반려 ──→ draft_answer
                                   └─ ANSWER, draft 없음 ──→ draft_answer ─┘
  ```

  - `ANSWER`인데 `draft`가 없거나 형식이 틀리면 지금처럼 `draft_answer`로 간다.
  - 반려되면 지금처럼 사유를 붙여 `draft_answer`(답 전용 프롬프트)로 다시 쓴다.
  - 빠른 명령은 Tool을 받은 뒤 지금처럼 `draft_answer`로 바로 간다(고르기 호출이 없음).
- **재생성 예산은 그대로 하나다.** `plan_next_tool`이 쓴 초안은 첫 생성 1회로 센다. 그 호출이 `LlmClient.generate` 안에서 형식 실패로 다시 만든 횟수도 더한다. `draft_answer`는 남은 횟수만큼만 다시 생성한다. 합쳐 3회가 상한이다.
- **기록**: 초안을 쓴 고르기 호출도 task는 `agent_plan`으로 남긴다(호출 종류가 아니라 단계 이름). 응답의 `model`·`generatedAt`은 답 초안을 만든 호출의 값이다.
- **검토를 거치지 않는 답의 범위**: LLM이 만든 답은 모두 `review_answer`를 거친다(초안을 고르기 호출이 썼어도 같음). LLM 없이 코드가 만든 정해진 안내(#631)와 `OUT_OF_SCOPE`는 근거·숫자가 없는 고정 문구이므로 검토 노드 대상이 아니다. 이 문장이 ADR-0045 '지켜야 할 것'의 '검토 노드를 거치지 않은 답을 내보내지 않는다'를 구체화한다.
- `PROMPT_VERSION`을 올린다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
| --- | --- |
| 지금처럼 두고 Tool 고르기에 빠른 작은 모델만 쓰기 | 고르기 한 번의 시간(약 3초)은 줄지만 호출 수는 그대로다. 모델 바꾸기는 품질 측정이 필요해 #633에서 따로 본다. 두 방법은 함께 쓸 수 있다 |
| 처음부터 답 쓰기와 Tool 고르기를 늘 한 호출로(매번 답 초안을 쓰게) | Tool이 필요한 단계에서도 답 초안을 쓰느라 출력이 늘고, 자료 없이 쓴 초안은 버려진다. '충분'할 때만 쓰게 하는 편이 낭비가 적다 |
| 검토도 같은 호출에서 LLM에게 맡기기 | 검사 항목이 모두 코드 규칙으로 판정되고, LLM 판정은 재현되지 않는다(ADR-0045와 같은 이유) |
| 답 쓰기 노드를 없애고 반려도 고르기 노드가 다시 쓰기 | 반려 사유를 붙여 다시 쓸 때는 Tool 목록이 필요 없다. 답 전용 프롬프트가 입력이 작고 지금 검증된 흐름이다 |

## 결과

- 좋아지는 점: 가장 흔한 흐름에서 LLM 호출이 3번에서 2번으로 줄어 채팅마다 약 3초와 입력 약 5~6천 토큰이 준다(목표 측정은 #632 PR에 적음). 검사·예산·기록 규칙은 그대로다.
- 감수하는 점: 계획 프롬프트가 답 규칙까지 담아 길어지고, 출력 형식(스키마)이 커진다. 고르기 호출이 답까지 쓰는 경우 그 호출은 지금보다 오래 걸린다(답 쓰기와 비슷). 계획 프롬프트와 답 프롬프트에 같은 답 규칙이 두 번 있으므로 한쪽만 고치지 않도록 한 상수에서 만든다.
- 지켜야 할 것
  - 답 규칙은 `prompt.py`의 한 곳(상수)에서 만들어 계획·답 프롬프트가 함께 쓴다.
  - LLM이 만든 답은 어느 노드가 썼든 `review_answer`를 거친다.
  - 재생성 예산을 노드마다 따로 세지 않는다.

## 다시 볼 때

- 답을 쓴 고르기 호출의 검토 반려율이 답 전용 프롬프트보다 눈에 띄게 높을 때(그때는 초안을 버리고 `draft_answer`만 쓰도록 되돌림)
- Tool 고르기에 작은 모델을 쓰기로 정할 때(#633). 작은 모델이 답 초안까지 쓰면 품질이 달라지므로 고르기와 답 쓰기를 다시 나눌지 본다
- 답을 스트리밍으로 보내야 할 때
